# BodySense 本地 ASR 对比：`ggml-base.bin` vs `ggml-small.bin`

## 背景

为了判断 BodySense 在批量导入合作视频时，默认应该使用哪一档本地 ASR 模型，本次基于同一条试点素材 `头前移.mp4` 的导出音频，比较了 `whisper.cpp` 的 `ggml-base.bin` 与 `ggml-small.bin`。

目标不是追求论文级评测，而是回答一个更实际的问题：

> 在当前这台开发机上，`small` 相比 `base`，转录质量提升是否足以覆盖更高的时间和内存成本？

## 测试环境

- 机器：Intel Core i7-14650HX
- CPU 核心 / 线程：16 / 24
- 内存：31.78 GB
- 运行方式：`ffmpeg` Whisper filter，底层为本地 `whisper.cpp`
- 推理模式：`use_gpu=false`
- 语言参数：`language=zh`
- 输入音频：`apps/ai-service/data/knowledge_sources/凯圣王-forward-head-posture-头前移/audio.wav`
- 音频时长：346.23 秒，约 5 分 46 秒

## 测试方法

两档模型使用完全一致的条件：

- 同一份 `audio.wav`
- 同一台机器
- 同样的 `ffmpeg` 调用方式
- 同样的语言参数 `zh`
- 同样关闭 GPU

统计项包括：

- 模型文件大小
- 转录耗时
- RTF（real-time factor，转录耗时 / 音频时长）
- 峰值工作集内存
- 峰值私有内存

说明：

- Windows 下 `ffmpeg` 会拉起一个轻量前台进程和一个真正工作的子进程。
- 本次内存统计采用“同一批次启动的全部 `ffmpeg` 进程总占用峰值”，避免只抓到前台壳进程而低估内存。

## 结果总览

| 指标 | `ggml-base.bin` | `ggml-small.bin` | 差异 |
| --- | ---: | ---: | ---: |
| 模型文件大小 | 141.10 MB | 465.01 MB | `small` 是 `3.30x` |
| 转录耗时 | 189.19 s | 401.96 s | `small` 是 `2.12x` |
| RTF | 0.55 | 1.16 | `base` 快于实时，`small` 慢于实时 |
| 峰值工作集总内存 | 346.22 MB | 812.72 MB | `small` 是 `2.35x` |
| 峰值私有内存总量 | 825.62 MB | 1293.42 MB | `small` 是 `1.57x` |
| 单个最重进程峰值工作集 | 336.35 MB | 802.73 MB | `small` 是 `2.39x` |
| 输出转录文件大小 | 11.99 KB | 11.29 KB | 接近 |

## 质量抽样

本次没有人工逐字标注 ground truth，而是抽了两段术语密集区域做质检：

1. `02:49-03:16`：胸锁乳突肌松解与拉伸
2. `03:45-04:07`：后枕下 / 枕下肌群放松

### 抽样观察 1：句子完整性

`small` 的句子整体更连贯，口语衔接词更自然。

例子：

- `base`：`首先第一次问了`
- `small`：`首先第一步呢`

这类差异说明 `small` 在普通口语连贯性上更稳，后续自动分段时也更不容易被碎片化文本干扰。

### 抽样观察 2：动作描述更顺，但专业词仍然容易错

在“网球放松后枕下区域”这段里，`small` 对动作流程的句式更顺，比如：

- `base`：`可以准备一个网球 放在我们头...`
- `small`：`可以准备一个网球... 先压在这儿 然后平躺下去`

但解剖词依然没有被稳定识别出来：

- `枕外隆突`
- `枕下肌群`
- `胸锁乳突肌`
- `肩胛提肌`

这些词在两档模型里都仍然会出现误识别，只是 `small` 通常比 `base` 更接近原句结构。

### 抽样观察 3：`small` 不是“免精修”

`small` 的提升是存在的，但还远远没有达到“直接入知识库无需人工审核”的程度。尤其在 BodySense 这种场景里，真正关键的不是日常口语，而是：

- 体态名词
- 肌肉 / 解剖结构
- 动作步骤
- 风险提醒

这些恰好是最怕错字的部分。

## 对批量落地的意义

### 如果默认用 `base`

优点：

- 更轻
- 更快
- CPU 上已经快于实时
- 批量跑 6 个视频时，总等待时间更可控

缺点：

- 口语碎片更明显
- 术语误识别更多
- 自动知识分段和关键词分类更容易被脏文本带偏

### 如果默认用 `small`

优点：

- 句子连贯性更好
- 动作描述更顺
- 后续人工阅读和精修成本会下降一些

缺点：

- 时间成本明显上升
- 内存占用明显上升
- 在当前 CPU-only 模式下已经慢于实时
- 对专业术语的识别依然不够稳，不能指望它完全替代人工精修

## 当前建议

基于这次试点，推荐分两层看：

### 1. 如果目标是“先把 6 个视频尽快铺底稿”

优先用 `ggml-base.bin`。

理由：

- 跑得更快，适合先把全量转录、初稿分段和 clip 导出铺出来
- 虽然转录更脏，但对于“先跑通批量流程”更划算

### 2. 如果目标是“减少高价值视频的精修时间”

优先用 `ggml-small.bin`。

理由：

- 文本更顺一些，人工读稿和结构化整理会轻松一点
- 但它仍然不是“免精修模型”，只能减少工作量，不能消灭审核环节

## 推荐的实施策略

最务实的方案不是二选一，而是分层使用：

1. 批量底稿阶段：默认 `base`
2. 高价值视频复跑阶段：对重点视频再用 `small`
3. 人工精修阶段：只在人真正要看的视频上花时间

这个策略能同时兼顾：

- 批量速度
- 本地机器资源
- 精修效率

## 后续建议

下一步可以继续补两件事：

1. 单独测试 `ggml-medium.bin`
   重点看它在当前机器上的时间和内存是否已经超过可接受范围，以及对专业术语是否有明显跃升。
2. 做一版“术语纠错层”
   例如在 ASR 后加一个基于体态词表的纠错步骤，把 `胸锁乳突肌 / 肩胛提肌 / 枕下肌群 / 肩峰` 这类高频术语统一校正。  
   对 BodySense 来说，这一步很可能比继续盲目堆更大 ASR 模型更划算。
