**文档版本**：v1.0

## 1. 产品概述

### 1.1 产品简介

本产品是一款面向健身/运动爱好者和青少年/学生群体的 Web 端 AI 应用，核心目标是帮助用户理解自己的身体状态、识别体态问题，并获得个性化的改善方案。产品以体态评估与健康咨询为核心，通过 AI 大模型驱动的自然对话，结合专业知识库，为用户提供科学、易懂的身体分析和改善建议。

### 1.2 产品定位

**一句话定位**：你的 AI 体态健康顾问——帮你读懂身体，科学改善体态。

**核心价值**：

- **降低认知门槛**：将专业体态知识转化为通俗易懂的对话交互，用户不需要医学背景也能理解自己的身体问题。
- **个性化分析**：基于用户提供的身体信息、体态照片、体检报告等，给出针对个人的评估和建议。
- **引导式问诊**：不像传统搜索那样需要用户自己描述问题，AI 会主动引导用户补充关键信息，逐步缩小问题范围。

### 1.3 目标平台

Web 端应用（PC / 移动端浏览器自适应）。

### 1.4 命名决策记录 (Naming Decision)

- **中文名称**：体悟 (Tiwu)
- **英文名称**：BodySense
- **寓意**：双关语。既是常用词“体悟”（亲身体验与领悟），又拆解为**“对身体（体）的觉察与醒悟（悟）”**。体态的改善，始于对身体姿态的重新“觉悟”。
- **品牌气场**：禅意、深邃、高级。

## 2. 目标用户

### 2.1 核心用户群

**健身/运动爱好者**：关注体态对运动表现的影响，可能有运动损伤或慢性疼痛（如训练后腰疼、膝盖不适等），希望了解问题根源并获得针对性改善方案。

**青少年/学生**：处于身体发育阶段，长时间久坐学习可能导致体态问题（如驼背、颈椎前伸），本人或家长关注体态矫正和日常习惯改善。

### 2.2 用户特征

- 没有专业医学或运动解剖学知识，对自身问题只能做模糊描述（如"肩膀有点不舒服""腰经常酸"）。
- 希望获得清晰、具体的解释和可执行的改善方案，而不是笼统的建议。
- 使用 Web 浏览器访问，期望体验流畅、交互自然。

## 3. 功能模块

产品包含两大核心场景模块：**身体信息构建与评估** 和 **健康咨询工作台**。

### 3.1 模块一：身体信息构建

用户首次进入应用时，通过分步引导完成身体信息的采集，为后续的评估和咨询提供基础数据。

#### 3.1.1 基础信息采集（必选）

采用分步表单/对话式引导的方式收集以下信息：

| 信息项 | 说明 | 示例 |
|---|---|---|
| 性别 | 男/女/其他 | 男 |
| 年龄 | 数字输入 | 24 |
| 身高/体重 | 用于计算 BMI 等基础指标 | 175cm / 70kg |
| 职业/日常活动类型 | 久坐、久站、体力劳动等 | 程序员，日均久坐 10h |
| 日常作息 | 睡眠时间、作息规律性 | 凌晨 1 点入睡，8 点起床 |
| 运动习惯 | 运动类型、频率、时长 | 每周跑步 3 次，每次 30 分钟 |
| 既往伤病/手术史 | 已知影响体态的伤病史 | 右膝半月板损伤 |

**交互要求**：采用友好的对话式或卡片式引导，避免一次性大表单造成用户流失。每一步有简短说明，解释为什么需要这个信息（如"了解你的作息有助于判断肌肉恢复情况"）。

#### 3.1.2 详细信息上传（可选）

用户可以自主选择上传以下补充材料，用于丰富个人健康档案：

**体态照片**：支持上传正面、侧面、背面的全身站姿照片。照片作为辅助参考存档，不做 AI 自动识别分析（后续版本可考虑加入 AI 视觉分析能力）。提供拍摄指引（如"请站在墙前，自然放松，拍摄侧面全身照"）。

**体检报告**：支持上传体检报告图片或 PDF，重点关注体内维生素、微量元素含量等数据。通过 OCR + 大模型提取关键指标，存入用户档案。

#### 3.1.3 用户自我描述

提供一个开放式文本输入区域，引导用户用自己的话描述当前的身体感受和困扰。提供引导性问题辅助用户表达，例如：

- "你目前最困扰的身体问题是什么？"
- "什么时候开始感觉到这个问题的？"
- "日常生活中哪些动作会让你不舒服？"

#### 3.1.4 健康评估报告

信息收集完成后，系统基于已收集的数据生成一份初步的健康评估报告，包含：

**健康等级评分**：以直观的等级（如 A/B/C/D 或 5 星制）给出整体健康评估，附带各维度的分项得分（体态、运动能力、生活习惯等）。

**主要问题识别**：列出基于当前信息初步识别的体态问题或健康风险，以优先级排序。

**改善/保持方案概要**：针对识别的问题给出改善方向概述（具体方案在咨询工作台中深入展开），包含饮食建议、运动建议、日常习惯调整等维度的简要说明。

**评估报告需明确标注**：本报告仅供参考，不构成医疗诊断。如存在持续疼痛或严重不适，建议前往专业医疗机构就诊。

### 3.2 模块二：健康咨询工作台

这是产品的核心交互场景，采用**左右分栏工作台**布局。

#### 3.2.1 整体布局

**左侧 — 对话区**：用户与 AI 的自然语言对话窗口，承载问诊、问答、方案讨论的全部交互。

**右侧 — 信息面板**：实时更新的问诊信息与身体可视化区域，随对话进程动态刷新。右侧面板分为两个子区域：

- **结构化信息区**：以结构化卡片形式展示 AI 从对话中实时提取的症状信息，包括——涉及部位、症状类型（疼痛性质、持续时间、触发场景等）、已排除的可能性、当前倾向的判断方向。每条信息支持用户确认或修改。
- **身体可视化区**：展示人体示意图（正面/侧面/背面），在对话涉及具体身体部位时高亮标注对应区域，帮助用户直观理解当前讨论的问题涉及哪些肌肉、骨骼或关节。

#### 3.2.2 对话问诊流程

**第一阶段：问题描述与引导**

用户描述自己的体态问题或不适感受。AI 基于用户已有的身体档案信息进行初步分析，同时主动引导用户补充关键细节。

关键交互设计——**症状术语辅助**：当用户描述症状时，如果涉及专业术语或容易混淆的描述词，系统提供即时解释。具体实现方式为：

- **高亮链接形式**：对话中的关键术语（如"刺痛""钝痛""放射痛""麻木感"）以高亮链接呈现，用户点击后弹出简明定义和示例描述，帮助用户更准确地理解和选择自己的症状类型。
- **引导式追问**：当用户描述模糊时，AI 主动提供选项引导细化，例如："你说的'肩膀疼'，是以下哪种感觉？① 酸胀感，按压时会舒服一些 ② 尖锐的刺痛，特定角度会加重 ③ 持续的钝痛，活动后反而减轻 ④ 其他（请描述）"。
- **积极信息采集**：AI 不应仅被动等待用户描述，还应主动询问容易被忽略但诊断价值高的信息，例如：症状出现的时间规律（晨起/运动后/久坐后）、是否与特定动作相关、两侧是否对称、近期是否有变化等。

**第二阶段：可能性分析**

AI 综合对话信息和用户档案，给出一个或多个可能的体态问题判断。每个判断需包含：

- **问题名称**：通俗易懂的名称（如"上交叉综合征/圆肩"）。
- **匹配依据**：基于用户提供的哪些信息做出这个判断，让用户理解推理过程。
- **典型表现描述**：该问题的常见症状和表现，帮助用户对照自身情况确认。
- **严重程度评估**：轻度/中度/重度的初步判断。
- **置信度提示**：以直观方式（如高/中/低）提示该判断与用户描述的匹配程度。

如有多个可能判断，按匹配度排序展示，并说明各判断之间的区别和关联。

**第三阶段：用户确认与方案生成**

用户在多个可能判断中选择/确认最符合自身情况的诊断（可以选多个或补充修改）。确认后，AI 生成针对性的改善方案，包含：

- **针对性矫正动作**：具体的拉伸、强化练习动作，附带动作描述和注意事项（如可结合知识库中的视频资源进行说明）。
- **日常习惯调整**：坐姿、站姿、睡姿等方面的具体改善建议。
- **饮食/营养建议**（如涉及）：当问题与营养相关时给出饮食调整建议。
- **预期改善周期**：大致的改善时间线参考。
- **警示信号**：出现哪些情况时应停止自我改善并寻求专业医疗帮助。

#### 3.2.3 会话保存

每次咨询会话的完整对话记录和右侧面板的结构化信息应作为一次咨询记录保存，用户可在历史记录中回看。

### 3.3 模块三：训练计划与进度追踪

用户在完成初次评估和咨询后，系统基于识别的体态问题生成持续性的增强/恢复训练计划，并支持后续执行追踪和效果反馈。

#### 3.3.1 训练计划生成

**触发时机**：用户在咨询工作台中确认诊断后，系统自动询问是否生成训练计划；或用户在个人档案页主动点击"生成训练计划"按钮。

**计划内容结构**：

| 维度 | 说明 |
|---|---|
| 训练目标 | 针对当前体态问题的改善目标（如"缓解圆肩症状""增强核心肌群稳定性"） |
| 训练周期 | 建议的训练时长（如 4 周 / 8 周），分为若干阶段 |
| 每日/每周任务 | 具体的训练动作清单，包含动作名称、组数、次数、休息时间等 |
| 动作详解 | 每个动作的文字描述、注意事项、常见错误提示，可关联知识库中的视频资源 |
| 强度梯度 | 从低到高的难度递进设计，适应不同基础的用户 |
| 休息日安排 | 明确哪些天需要休息或做轻度活动 |
| 预期里程碑 | 各阶段结束时预期达到的改善效果 |

**个性化调整因素**：训练计划生成时综合考虑以下因素进行个性化定制——用户的年龄、体能基础、可用训练时间（用户可设置每天可用于训练的时间段）、是否有器械条件、既往伤病史限制等。

#### 3.3.2 训练执行与打卡

**每日训练界面**：展示当天的训练任务清单，用户可逐项完成并标记为"已完成"。每个动作卡片包含动作名称、图示/视频链接、组数次数要求、完成勾选框。

**打卡机制**：用户完成当日全部训练任务后，可进行打卡操作。系统记录连续打卡天数、总完成次数等激励数据。

**灵活调整**：用户可跳过某一天的训练（如身体不适、外出等），系统自动顺延后续计划；也可手动调整某天的训练强度（如减少组数）。

**训练日志**：用户可在每次训练后添加简短的文字记录，描述训练感受、是否有不适、完成情况等，供后续复盘参考。

#### 3.3.3 进度追踪与反馈

**可视化进度面板**：以图表形式展示训练执行情况，包括——连续打卡天数、本周完成率、累计训练次数、各阶段完成进度条等。

**体态改善对比**：用户可定期上传新的体态照片，系统与之前的照片并列展示，直观对比体态变化（此功能依赖用户上传，不做 AI 自动分析）。

**阶段性复评**：在训练计划的每个阶段结束时（如第 4 周末尾），系统引导用户进行一次简短的自我评估，回答关于症状变化的问题，AI 基于反馈给出下一阶段的调整建议。

**AI 动态调整**：根据用户的训练日志、打卡情况和阶段性复评结果，AI 可对后续训练计划进行动态优化——如增加难度、替换不适用的动作、延长某个阶段的时长等。

#### 3.3.4 提醒与激励

**训练提醒**：用户可设置每日训练提醒时间，系统在指定时间通过站内通知或邮件/短信（视实现方案而定）推送提醒。

**成就系统**：设置简单的成就徽章（如"连续 7 天打卡""完成第一阶段训练"等），增强用户坚持训练的动力。

**社区分享**（可选，后续版本考虑）：用户可选择将自己的训练成果分享到社区，与其他用户交流经验。

## 4. 知识库构建方案

### 4.1 知识库来源

知识库以一位专业 B 站 UP 主的视频内容为核心来源，构建步骤如下：

1. **内容提取**：对 UP 主的相关视频进行字幕/语音转文字，提取其中的体态知识、动作讲解、案例分析等内容。
2. **结构化整理**：将提取的内容按体态问题分类整理（如圆肩、骨盆前倾、脊柱侧弯等），形成结构化的知识条目。
3. **质量校验**：对入库内容进行基础校验，确保信息与主流运动康复/体态矫正知识不矛盾。
4. **补充扩展**：在 UP 主内容未覆盖的领域，引入公开的医学/运动科学资料进行补充。

### 4.2 知识库应用方式

- AI 在对话问诊和方案生成时，优先检索知识库中的相关内容作为回答依据。
- 方案中的矫正动作描述优先引用知识库中 UP 主的讲解方式，保持专业性和一致性。
- 知识库内容定期随 UP 主更新视频而同步扩充。

## 5. 数据存储方案

### 5.1 选定方案：云端存储 + 用户账号体系

产品采用**云端存储 + 用户账号**作为数据存储方案，理由如下：

- **多设备同步**：用户可在不同设备上登录同一账号，查看完整的身体档案和咨询历史。
- **数据持久化**：避免浏览器清除缓存导致数据丢失，确保长期追踪的连续性。
- **历史对比与进度追踪**：支持多次评估结果的对比分析、体态改善进度的可视化展示。
- **个性化推荐基础**：云端积累的用户行为数据和健康档案为后续智能推荐提供数据支撑。

### 5.2 数据库选型建议

| 数据类型 | 推荐数据库 | 说明 |
|---|---|---|
| 用户基础信息、会话记录、评估报告 | **PostgreSQL**（关系型） | 结构化数据，支持复杂查询和事务，适合用户档案、问诊记录等 |
| 知识库向量 Embedding | **Milvus / Qdrant**（向量数据库） | 支持高维向量相似度检索，用于 RAG 场景的知识库召回 |
| 体态照片、体检报告图片/PDF | **对象存储**（如 AWS S3 / 阿里云 OSS） | 非结构化文件存储，配合 CDN 加速访问 |
| 会话实时缓存、短期状态 | **Redis**（键值存储） | 高速读写，用于对话上下文缓存、用户会话 Token 管理等 |

### 5.3 核心数据模型概览

**用户表（users）**：用户 ID、手机号/邮箱、密码哈希、注册时间、最后登录时间等。

**身体档案表（user_profiles）**：关联用户 ID，存储性别、年龄、身高、体重、职业、作息、运动习惯、既往伤病史等。

**上传材料表（user_uploads）**：关联用户 ID，存储体态照片 URL、体检报告 URL、OCR 提取结果、上传时间等。

**咨询会话表（consultation_sessions）**：关联用户 ID，存储每次咨询的完整对话记录（JSON 格式）、右侧面板结构化信息、创建时间、结束时间等。

**评估报告表（assessment_reports）**：关联用户 ID，存储每次生成的健康评估结果（健康等级、问题列表、改善方案概要等）。

**知识库条目表（knowledge_entries）**：存储从 B 站 UP 主视频中提取的结构化知识，包含问题分类、标题、内容摘要、Embedding 向量 ID、来源视频信息等。

### 5.4 隐私与合规

- 所有敏感个人信息（PII）在数据库中加密存储，传输过程使用 HTTPS/TLS 加密。
- 符合《个人信息保护法》要求，用户可随时查看、修改、删除自己的全部数据。
- AI 对话数据不用于模型训练，除非用户明确授权。
- 文件存储（照片/报告）设置访问权限控制，仅用户本人和授权服务可访问。

## 6. 技术架构概要

### 6.1 技术选型

| 层级 | 技术栈 | 说明 |
|---|---|---|
| 前端 | **React** | 构建响应式 Web 应用，组件化开发，生态成熟，适合复杂交互界面 |
| 后端 | **Go** | 高并发、高性能，适合作为 API 网关和业务逻辑层，资源占用低 |
| AI 层 | **Python** | 大模型调用、RAG 检索、NLP 处理的主流语言，库生态丰富 |

### 6.2 前端（React）

- 基于 React 构建 SPA（单页应用），采用响应式设计适配 PC 和移动端浏览器。
- 咨询工作台采用左右分栏布局（移动端可切换为上下布局或 Tab 切换），利用 React 状态管理实现对话区与右侧面板的实时联动。
- 身体可视化区域使用人体解剖示意图（SVG 或 Canvas 实现），支持部位高亮交互。
- 推荐搭配 React Router 做页面路由，Zustand / Redux 做全局状态管理，TailwindCSS 或 Ant Design 做 UI 组件库。

### 6.3 后端（Go）

- Go 服务作为核心业务层，负责：用户鉴权与会话管理、API 路由与请求转发、业务逻辑处理（如信息校验、数据持久化）、文件上传与管理（体态照片、体检报告）。
- Go 服务同时作为 AI 层的网关代理，前端不直接调用 Python AI 服务，而是通过 Go 后端转发，统一鉴权和限流。
- 如采用本地存储方案：Go 后端仅承担 AI API 网关职责（鉴权 + 转发）。
- 如采用云端存储方案：Go 后端承担完整业务服务，包括用户服务、数据存储、文件存储等模块。

### 6.4 AI 层（Python）

- Python 服务独立部署，通过 HTTP/gRPC 与 Go 后端通信。
- **大语言模型（LLM）**：负责自然语言交互、问诊引导、信息提取、方案生成。Python 侧封装 LLM API 调用（如 OpenAI / Claude / 国内大模型 API），支持流式输出（SSE / WebSocket）。
- **知识库检索（RAG）**：对话过程中实时检索知识库中的相关内容，作为 LLM 回答的上下文补充。使用向量数据库（如 Milvus / Qdrant / Weaviate）存储知识库 Embedding，Python 侧实现检索和上下文拼装。
- **OCR 能力**：用于体检报告图片的文字识别和关键指标提取（可使用 PaddleOCR / Tesseract 等）。
- **对话记忆管理**：维护单次咨询会话的上下文窗口，控制 token 用量，确保对话连贯性。

### 6.5 整体架构示意

```
┌─────────────────┐       HTTP/WebSocket        ┌─────────────────┐
│    React 前端    │  ◄──────────────────────►  │    Go 后端       │
│  (浏览器 SPA)   │                             │  (API 网关+业务) │
└─────────────────┘                             └────────┬────────┘
                                                         │ HTTP / gRPC
                                                         ▼
                                                ┌─────────────────┐
                                                │  Python AI 服务  │
                                                │ (LLM + RAG+OCR) │
                                                └────────┬────────┘
                                                         │
                                                ┌────────▼────────┐
                                                │   向量数据库     │
                                                │  (知识库检索)    │
                                                └─────────────────┘
```

## 8. 非功能性需求

### 8.1 性能

- 首屏加载时间 ≤ 3 秒。
- AI 对话响应时间 ≤ 5 秒（首 token 响应 ≤ 2 秒，采用流式输出）。
- 右侧面板信息更新延迟 ≤ 1 秒（对话结束后）。

### 8.2 兼容性

- 支持主流浏览器：Chrome、Safari、Edge、Firefox 最新两个主要版本。
- 移动端浏览器适配：iOS Safari 15+、Android Chrome 90+。

### 8.3 隐私与安全

- 用户上传的体态照片和体检报告属于敏感个人信息，传输过程需加密（HTTPS）。
- 如采用云端存储，数据存储需加密，并符合《个人信息保护法》相关要求。
- 用户可随时删除自己的全部数据。
- AI 对话数据不用于模型训练（除非用户明确授权）。

### 8.4 可用性

- 对话式交互需支持容错：用户输入不规范或信息不完整时，AI 应友好引导而非报错。
- 知识库内容缺失时，AI 应诚实告知并给出通用建议，而非编造信息。
