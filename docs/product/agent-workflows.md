# BodySense · Agent 工作流与交互工具

## 1. Agent 的职责

Agent 负责解析用户意图，选择合适的证据采集和业务工具，解释操作结果并提出下一步建议。工具的结构化返回结果及业务后端负责最终事实和状态权威。

处理顺序：

~~~text
用户消息 / 图片 / 选中的人体部位
         ↓
理解主体、部位、时间、事实/推测、意图
         ├── 普通知识问题 ──→ 直接解释
         ├── 明确本人事实 ──→ BodyState 验证与自动保存
         ├── 歧义/同时间冲突 ──→ ask_user → 继续处理该字段
         ├── 正式分析请求 ──→ 分析/证据审查 → Diagnosis 局部补丁
         ├── 计划修改请求 ──→ 定位计划/验证授权 → 定向修改
         └── 发现训练影响 ──→ 只读影响检查 → 建议 → 用户决定
                                        ↓
                        返回实际提交状态 / 当前业务投影
~~~

3D 人体选区、图片上传和示范动作默认只作为交互上下文或原始资料；不能自动转换成医学事实。

## 2. 上下文装配

每次运行按当前任务装配：
- 相关当前 BodyState、有效安全限制与必要病程；
- 当前综合 Diagnosis 的相关病情及证据；
- 当次问题涉及的 TrainingPlan 与执行约束；
- 最近对话与按需检索的相关历史；
- 用户当前选中的人体部位、开放的业务窗口及工具模式。

不用每轮加载完整聊天、全部历史、所有计划；检索到的旧陈述必须与当前事实、更正及时间语义核对。

## 3. 逻辑工具集合

工具名称是建议的职责命名，具体可映射到业务 API：

| 逻辑工具 | 允许的结果 | 关键防护 |
| --- | --- | --- |
| record_body_state | 自动提交明确的本人事实与时间变更 | 身份、来源、时间、幂等与冲突检查 |
| ask_user | 追问具体歧义并等待回答 | 必须绑定待回答字段和目标事实 |
| inspect_evidence | 获取和审阅照片、资料、自测与知识证据 | 不能推定没有证据支持的医学事实 |
| analyze_conditions | 在用户授权的范围内分析病情 | 使用固定 BodyState 快照、给出不确定性 |
| confirm_condition | 在 Chat 中让用户核对病名、原因和处理方案 | 用户确认 Agent 分析不等于临床确诊；未确认不可写入正式条目 |
| apply_diagnosis_patch | 原子更新综合 Diagnosis 内已确认的目标条目 | 正式分析授权、确认工具记录、证据/安全门禁、并发校验 |
| inspect_plan_impact | 检查新情况对所有相关计划的影响 | 只读，不修改训练内容 |
| propose_plan_change | 生成受影响计划、理由和具体差异 | Agent 建议保持 pending |
| apply_plan_change | 提交指定 Plan 的局部修改 | 验证用户请求或已接受提案、目标和底版 |
| open_business_window | 在原型对应窗口呈现当前对象或工具 | 无任何持久化业务副作用 |

### 3.1 自动记录

1. 读取当前消息与必要上下文，提取每个本人陈述。
2. 根据主体、时间、部位、语义和来源进行验证。
3. 将明确事实打包成一次或少量语义一致的幂等事务。
4. 对不能安全确定的字段创建单独待澄清项。
5. 收到后端确认后反馈「已记录：……」；失败时明确说明，不伪称成功。

第三人陈述、疾病知识提问、AI 自己提出的解释不走自动事实写入。已保存的事实可通过更正操作修正。

### 3.2 正式 Diagnosis

1. 用户明确提出新分析、局部更新或综合重评估。
2. Agent 确定受影响的病情范围和所需证据，必要时使用工具补充信息。
3. 形成带明确病名、原因分析、处理方案以及来源、反证、确定性局限的**待确认提案**；若无法明确，不创建正式病情。
4. Agent 调用 confirm_condition，通过 Chat 工具展示完整提案，让用户确认或继续补充。用户请求分析不是代替这个结果确认步骤；确认记录绑定准确的提案身份和内容。
5. Go 业务规则执行医学安全、证据、确认来源与并发审查；明确区分「用户认可 Agent 分析」和「临床确诊」。
6. 验证通过后，只对目标 ConditionEntry 应用补丁，并原子产生一次整体修订；拒绝、取消或超时均不改正式 Diagnosis。
7. 返回完整当前综合 Diagnosis，不用局部结果覆盖整份聚合。

Agent 可建议需要诊断复核的原因，但在用户未授权时不得正式发表修订。安全阻断或证据不足须如实返回。

### 3.3 用户主动更改训练计划

1. 从用户请求中识别 planId 与动作/次数/时间等修改范围。
2. 校验 BodyState 的最新安全约束、当前计划修订与用户权限。
3. 生成范围受限的变更并提交指定计划。
4. 返回实际变更内容；其他计划完全不变。

请求内容模糊时使用 ask_user；破坏性或高风险变更执行额外必要保护，不反复请求与用户已经明确表达的同一授权。

### 3.4 Agent 主动提出计划调整

1. BodyState 出现与既有训练计划相关的新信息。
2. inspect_plan_impact 检查受影响的具体计划和动作。
3. 向用户展示「为什么建议检查」「影响哪个计划」「拟改什么」「可不修改」。
4. 生成待决定提案，用户选择接受或暂不修改。
5. **只有明确接受后**调用 apply_plan_change。
6. 用户拒绝、关闭、超时或网络失败时，计划内容保持原样。

安全风险可单独阻断执行或给予就医提示，不得借此改写计划。

## 4. 交互工具状态

每次待回答问题或待授权提案必须有稳定交互 ID、关联用户、关联消息、关联业务对象、过期/恢复语义。系统需支持：

- accept：应用准确的授权目标；
- reject：明确拒绝、保留原业务内容；
- cancel/close：结束交互，不当作接受；
- resume：以同一状态恢复对话任务；
- retry：幂等重试，重复回答不二次提交；
- stale：业务底版已变化时，重新核验与展示；
- fail：显示错误，避免虚假的成功反馈。

模型可对无效工具参数进行有限次纠错；不能绕过后端校验。所有正式分析及训练内容改动需可追溯到触发的用户请求或批准操作。

## 5. 安全处理

识别到需专业医疗评估的风险信号时，立即提供适当、安全的下一步；如有必要，可阻断不适当训练执行。不能把模型建议伪装成临床诊断，也不能将症状与训练时间相邻误写为已证明的因果关系。授权修改训练计划与安全执行门禁保持独立。
