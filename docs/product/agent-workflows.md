# BodySense · Agent 工作流与交互工具

**本文件定义 Agent 的处理流程、上下文与工具。** 业务规则见 [产品需求](./requirements.md)，字段与不变量见 [领域模型](./domain.md)，用户看到的界面见 [UI 与交互](./interface.md)。

## 1. Agent 的职责

Agent 负责解析用户意图，选择合适的证据采集和业务工具，解释操作结果并提出下一步建议。工具的结构化返回结果及业务后端负责最终事实和状态权威。

~~~text
用户消息 / 图片 / 选中的人体部位
         ↓
理解主体、部位、时间、事实/推测、意图
         ├── 普通知识问题 ──→ 直接解释（R-GEN-01）
         ├── 明确本人事实 ──→ BodyState 验证与自动保存（§3.1）
         ├── 歧义/同时间冲突 ──→ ask_user → 继续处理该字段
         ├── 正式分析请求 ──→ 分析/证据审查 → confirm_condition → Diagnosis 局部补丁（§3.2）
         ├── 计划修改请求 ──→ 定位计划/验证授权 → 定向修改（§3.3）
         └── 发现训练影响 ──→ 只读影响检查 → 建议 → 用户决定（§3.4）
                                        ↓
                        返回实际提交状态 / 当前业务投影
~~~

3D 人体选区、图片上传和示范动作默认只作为交互上下文或原始资料，不能自动转换成医学事实。

## 2. 上下文装配

每次运行按当前任务装配：

- 相关当前 BodyState、有效安全限制与必要病程；
- 当前 Diagnosis 的相关病情及证据；
- 当次问题涉及的 TrainingPlan 与执行约束；
- 最近对话与按需检索的相关历史；
- 用户当前选中的人体部位、开放的业务窗口及工具模式。

不用每轮加载完整聊天、全部历史、所有计划；检索到的旧陈述必须与当前事实、更正及时间语义核对。

## 3. 逻辑工具与流程

工具名称是建议的职责命名，具体可映射到业务 API：

| 逻辑工具 | 允许的结果 | 关键防护 | 规则 |
| --- | --- | --- | --- |
| record_body_state | 自动提交明确的本人事实、时间变更与用户本人提出的假设（BodyHypothesis） | 身份、来源、时间、幂等与冲突检查；不写入 AI 假设 | R-BS-01～06 |
| ask_user | 追问具体歧义并等待回答 | 必须绑定待回答字段和目标事实 | R-BS-03 |
| inspect_evidence | 获取和审阅照片、资料、自测与知识证据 | 不能推定没有证据支持的医学事实 | R-DX-08 |
| analyze_conditions | 在用户授权的范围内分析病情，创建 ConditionAnalysisRun 与若干 ConditionProposal | 使用固定 BodyState 快照、给出不确定性；不重复已拒绝的提案指纹（INV-13） | R-DX-02、R-DX-10、R-DX-11 |
| confirm_condition | 在 Chat 中逐个展示病情提案，记录用户决定（ConditionProposalDecision）或继续补充 | 决定绑定准确的 proposalId 与内容指纹；本身不写入 Diagnosis | R-DX-03～05、R-DX-08 |
| apply_diagnosis_patch | 运行内提案全部结算后，把所有生效决定作为一个原子补丁提交 | 正式分析授权、决定记录、来源/结论组合约束、证据/安全门禁、底版修订校验 | R-DX-01、R-DX-12、INV-04～06、INV-11～12 |
| inspect_plan_impact | 检查新情况对所有相关计划的影响 | 只读，不修改训练内容 | R-TP-05 |
| propose_plan_change | 生成受影响计划、理由和具体差异 | Agent 建议保持 pending | R-TP-04 |
| apply_plan_change | 提交指定 Plan 的局部修改 | 验证用户请求或已接受提案、目标和底版 | R-TP-03～04、INV-07 |
| open_business_window | 在对应窗口呈现当前对象或工具 | 无任何持久化业务副作用 | — |

### 3.1 自动记录 BodyState

1. 读取当前消息与必要上下文，提取每个本人陈述。
2. 根据主体、时间、部位、语义和来源进行验证。
3. 将明确事实打包成一次或少量语义一致的幂等事务。
4. 对不能安全确定的字段创建单独待澄清项（ask_user）。
5. 收到后端确认后反馈「已记录：……」；失败时明确说明，不伪称成功。

用户本人提出的怀疑（「我怀疑是……」）作为 BodyHypothesis（`source = user`）自动记录（R-BS-06）。第三人陈述、疾病知识提问、AI 自己提出的解释不写入 BodyState；AI 假设只记录在 ConditionAnalysisRun 中。已保存的事实可通过更正操作修正。

### 3.2 Diagnosis 正式分析与病情确认

1. 用户明确提出新分析、局部更新或综合重新分析（R-DX-02）；analyze_conditions 创建 ConditionAnalysisRun，固定 BodyState 与 Diagnosis 底版修订。
2. Agent 确定受影响的病情范围和所需证据，必要时使用工具补充信息；文件类证据只使用按 [证据管线](../architecture/health-document-evidence-pipeline.md) 规则采纳的结果（R-PS-03）。
3. 为每个需要新增、更新或结束的病情形成一个**病情提案**（ConditionProposal）：名称、原因分析、处理方案，以及来源、反证、确定性局限；三要素按 R-DX-11 如实填写，不为凑齐而编造。证据不足或安全阻断时如实返回，不创建提案（R-DX-10）。已被用户拒绝、且没有相关新证据 ID 的提案指纹不得再次提出（INV-13）。
4. 对每个提案调用 confirm_condition，在 Chat 中展示完整内容并记录用户决定：
   - Agent 分析 / 用户怀疑来源：「大概率是这个」「可能是，先保留」「不是这个」或继续补充（R-DX-04）；
   - 临床来源（临床文件 / 用户转述医生诊断）：「纳入我的病情管理」「不纳入」或继续补充；确认不改变来源（R-DX-08）。
5. 运行内提案全部结算后（含关闭、超时、底版变化的处理，见 [domain §3.3](./domain.md#33-多提案确认与原子提交)），Go 业务规则执行医学安全、证据、来源/结论组合约束、决定记录与并发审查。
6. 验证通过后由 apply_diagnosis_patch 按 [domain §3.2](./domain.md#32-用户选择与数据映射) 的映射，把所有生效决定作为一个原子补丁写入，只产生一次整体修订；没有生效决定时不产生修订。
7. 返回完整当前 Diagnosis，不用局部结果覆盖整份聚合。

「继续补充」会中断对该提案的决定：新信息按 §3.1 记录，Agent 可在同一运行内给出修订后的提案（旧提案 `superseded`），已作出的其他决定保留。用户关闭界面或之后重新进入对话时，以同一运行恢复未决定的提案。

### 3.3 用户主动更改训练计划

1. 从用户请求中识别 planId 与动作/次数/时间等修改范围。
2. 校验 BodyState 的最新安全约束、当前计划修订与用户权限。
3. 生成范围受限的变更并提交指定计划。
4. 返回实际变更内容；其他计划完全不变。

请求内容模糊时使用 ask_user；破坏性或高风险变更执行额外必要保护，不反复请求用户已经明确表达的同一授权（R-TP-03）。

### 3.4 Agent 主动提出计划调整

1. BodyState 出现与既有训练计划相关的新信息。
2. inspect_plan_impact 检查受影响的具体计划和动作。
3. 向用户展示「为什么建议检查」「影响哪个计划」「拟改什么」「可不修改」。
4. 生成待决定提案，用户选择「接受调整」或「暂不修改」。
5. **只有明确接受后**调用 apply_plan_change。
6. 用户选择「暂不修改」（提案 rejected）、关闭界面（提案保持 pending，可恢复）、超时或底版变化（提案 expired）或网络失败时，计划内容保持原样（状态定义见 [domain §4](./domain.md#4-trainingplan)）。

## 4. 交互工具状态

每次待回答问题或待授权提案必须有稳定交互 ID、关联用户、关联消息、关联业务对象、过期/恢复语义。系统需支持：

- accept：应用准确的授权目标；
- reject：用户明确拒绝（「不是这个」「暂不修改」），保留原业务内容并记录决定；
- close：关闭界面或离开对话**不是拒绝也不是接受**，交互保持 pending；
- resume：以同一状态恢复对话任务（含未决定的病情提案与计划提案）；
- expire：超时或业务底版修订变化时失效，不产生内容修改；
- retry：幂等重试，重复回答不二次提交；
- stale：业务底版已变化时，重新核验与展示；
- fail：显示错误，避免虚假的成功反馈。

病情提案的状态与提交规则见 [domain §3.3](./domain.md#33-多提案确认与原子提交)，计划提案见 [domain §4](./domain.md#4-trainingplan)。

模型可对无效工具参数进行有限次纠错，不能绕过后端校验。所有正式分析及训练内容改动需可追溯到触发的用户请求或批准操作。

## 5. 安全处理

识别到需要就医检查的风险信号时，立即提供适当、安全的下一步；如有必要，在 BodyState SafetyState 中发布带风险等级、范围、有效期与解除条件的执行限制，由 Trainer 执行门禁（R-SAFE-01、R-SAFE-03）。不能把模型建议伪装成临床诊断，也不能将症状与训练时间相邻误写为已证明的因果关系（R-EX-02）。安全执行门禁与训练计划授权保持独立（R-SAFE-02）。
