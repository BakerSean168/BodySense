# BodySense · 验收规范与实施顺序

**说明**：本文件定义可观察的验收标准；测试项是否通过，应以真实实现后的单元、集成、端到端执行结果判定。

## 1. 业务验收矩阵

| ID | 用户输入 / 条件 | 必须满足的结果 |
| --- | --- | --- |
| BS-01 | 「我今天左肩痛」 | 无逐条确认直接保存；归属、左侧和时间正确 |
| BS-02 | 「朋友今天左肩痛」 | 不加入用户本人 BodyState |
| BS-03 | 「偏头痛是什么？」 | 解释知识，不新增本人疾病记录 |
| BS-04 | 「我怀疑自己有偏头痛」 | 保存用户推测，不按临床确诊保存 |
| BS-05 | 「医生告诉我患偏头痛」 | 标注为用户转述，不能伪装已核验报告 |
| BS-06 | 「去年左肩痛，现在好了」 | 历史发生与当前恢复并存，不误判矛盾 |
| BS-07 | 「我之前左右记反了」 | 纠正错误记录，不生成虚构病程 |
| BS-08 | 同时间同条件互斥记录 | ask_user 指出具体日期和条件；不覆盖不确定部分 |
| BS-09 | 同一条消息含多项明确事实和一处模糊 | 明确部分先保存，模糊部分独立待澄清 |
| BS-10 | 同一次写入重复提交 | 不出现重复 Fact 或重复 Revision |
| DX-01 | 用户仅闲聊症状 | 可以初步解释，不未经请求发布正式诊断 |
| DX-02 | 用户请求重评估病情 B，另有 A、C | B 改变，A/C 保持身份和内容，仍是一份综合 Diagnosis |
| DX-03 | 一次分析影响 A 与 B | 原子更新两项，整体 Revision 只增加一次 |
| DX-04 | 正式分析证据不足或有安全阻断 | 不制造确定性诊断，返回不足/阻断结果 |
| DX-05 | 页面查看当前诊断 | 默认只显示已核对病情的完整名称/原因/处理方案，不出现修订号/版本切换器 |
| DX-06 | AI 分析出可能病情，用户尚未确认 | 只保留在 Chat/分析提案；不得混进正式 Diagnosis 列表 |
| DX-07 | Chat 确认工具核对病名、原因、处理方案 | 仅用户确认过的目标条目成功入库；用户认可 Agent 分析不等于临床确诊 |
| DX-08 | 用户拒绝诊断提案或继续补充 | Diagnosis 无内容修订；相关 BodyState 事实不丢失 |
| TP-01 | 用户明确说「修改臀腿计划的深蹲」 | 定位目标计划，只修改明确授权的内容 |
| TP-02 | 用户报告腿麻，但尚未授权计划修改 | 可以建议调整，所有 TrainingPlan 内容保持不变 |
| TP-03 | 用户接受 Agent 指定提案 | 仅指定计划发生一次内容修订 |
| TP-04 | 用户拒绝、关闭或超时 | 计划内容保持不变 |
| TP-05 | 计划提案接受请求网络重试 | 幂等，只产生一次修订 |
| TP-06 | 出现严重训练风险 | 可以安全阻断训练执行，不静默重写计划 |
| TP-07 | 打开一份已接受训练计划 | 可见热身、正式训练及必要的放松，每个动作有名称、组数、次数/时长和整体频率 |
| TP-08 | 点击具体动作请求修改 | 定位到具体 Plan 与 exerciseId，其他动作和其他计划不被重建 |
| UI-01 | 桌面关闭/收起浮动窗口 | 可查看持续存在的 3D 人体场景 |
| UI-02 | 人体点选一个部位 | 仅形成上下文，不自动记录异常/疼痛 |
| UI-03 | Chat → 人体工具 → 返回 Chat | 上下文与待回答交互保持一致 |
| UI-04 | Person 查看身体、器材、资料 | 显示真实当前状态与恰当空态，不用演示数据 |
| UI-05 | 移动端切换业务窗口 | 任务与选区可恢复，主要操作可触达 |
| UI-06 | 878px 等窄桌面窗口打开 Diagnosis | 标题、已确认病情卡片及操作按钮都在可见范围内，不向右溢出 |
| UI-07 | Chat 展示病情确认工具 | 可以核对名称/原因/方案，确认与取消结果不同，不伪称在确认前已更新诊断 |
| SEC-01 | 使用别人的 planId / conditionId 写入 | 后端拒绝越权 |
| SEC-02 | 两个并发分析或计划修改 | 以修订并发控制避免覆盖他人的最新变更 |

## 2. 运行时必须维护的不变量

1. BodyState、Diagnosis 和每份 TrainingPlan 各有明确、唯一的业务拥有者。
2. 用户自述不会被模型转化为临床确诊；Observation/Hypothesis 与 Fact 不混同。
3. Correction 与 TemporalChange 是不同业务操作。
4. Diagnosis 的局部补丁不会删除或改写无关病情。
5. 同一 Diagnosis 原子补丁最多产生一个整体新修订。
6. 正式 Diagnosis 的创建/发表需要可追溯的用户请求及对病名、原因和处理方案的结果确认；单纯请求分析不代表接受 Agent 结论。
7. 未经用户授权绝不改变 TrainingPlan 的当前有效内容。
8. 训练安全阻断与计划内容修订的权限独立。
9. 工具、事件和网络重试具备幂等、错误提示和可恢复性。
10. 当前页面不暴露技术修订号、历史版本管理或后端运行编号。

## 3. 实施工作顺序

| 阶段 | 交付物 | 验收重点 |
| --- | --- | --- |
| P1 领域契约 | BodyState 自动写入和时间/来源模型；Diagnosis 当前聚合；Plan 级授权模型 | 类型、权限、不变量的契约测试 |
| P2 自述记录 | Agent 提取 → Go 校验提交 → 自动反馈、澄清恢复 | BS-01～10 |
| P3 综合 Diagnosis | 用户请求触发分析；Chat 用户确认工具；ConditionEntry 原子补丁 | DX-01～08 |
| P4 TrainingPlan | 每份计划的阶段化动作、组次/频率、只读影响检查和用户授权 | TP-01～08 |
| P5 交互集成 | 3D 桌面、浮动 Chat、Person、Diagnosis 与 Trainer 的真实数据状态 | UI-01～07 |
| P6 稳定化 | 数据权限、并发、事件恢复、安全门禁及端到端回归 | SEC-01～02 与全矩阵 |

每阶段均以真实输入 → Agent/工具 → 后端持久状态 → UI 读取的端到端闭环作为完成定义。只通过类型检查或静态页面检查不足以宣称业务完成。

## 4. 独立审核点

- 对照业务文档核查 API 与数据库，不得假设模型草案已被实现。
- 使用真实/模拟用户案例验证相对时间、主体归属、因果表述和医学确定性。
- 检查一条消息中多次工具调用是否发生部分成功、重复、失败或取消。
- 验证未授权建议只存为 Proposal，不修改训练内容；检查所有写操作的用户授权与并发修订。
- 对照 Penpot 的实际组件与交互核验桌面/移动界面，不能只比较静态截图。
