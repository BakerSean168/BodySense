# BodySense · 产品需求规格

**状态：产品业务规格 · 2026-10-12（业务规则唯一来源）**

本文件回答「做什么、为什么」，并为每条业务规则分配编号（`R-*`、`G-*`）。数据契约与不变量见 [领域模型](./domain/README.md)，流程与工具见 [Agent 工作流](./agent-workflows.md)，窗口与交互见 [UI 与交互](./interface.md)，测试矩阵见 [验收规范](./acceptance.md)。术语以 [术语表](./glossary.md) 为准。

## 1. 产品目标

BodySense 面向希望了解身体不适、体态、活动能力及训练情况的人群。用户可以自然描述身体变化，按需获取综合诊断，管理多份训练计划，并持续记录训练反馈；不需要理解内部 Agent 运行、对象修订或医学术语。

BodySense 提供健康信息整理、解释与辅助训练建议，不替代医生或其他专业人员的医学诊断与治疗。身体自述、客观观察、模型推测、临床诊断具有不同证据等级。

## 2. 业务规则

### 2.1 普通知识咨询

- **R-GEN-01**：用户提问一般健康知识、训练方法或讨论他人问题时，Agent 直接解释。知识问题、假设案例及第三人症状不写入本人的 BodyState。

### 2.2 BodyState 身体状态

- **R-BS-01 自动记录**：用户清晰表达自己的身体状态时，Agent 直接提取并写入，**无需逐条确认**。
- **R-BS-02 写入前提**：本人归属明确、语义可确定、时间不被虚构、来源可追踪。不能因 Agent 生成了某种医学推测就把推测写成用户事实。
- **R-BS-03 有歧义才追问**：仅当主体、身体部位、左右侧、发生时间、历史记录性质或执行对象不能明确时才追问，问题要具体；同一消息中可确定的其他事实照常记录，不因一处模糊而整体阻塞。
- **R-BS-04 时间与冲突**：区分以下四种情况——
  - **真实发展**：「之前左臀痛，现在好了」——保留真实病程，更新当前状态。
  - **记录更正**：「之前说左肩是口误，其实是右肩」——更正错误来源，不虚构病情迁移。
  - **重复**：对同一事件再次描述——去重或增加来源，不生成无意义副本。
  - **真正冲突**：同一时间、同一条件下状态互斥，且无法用上下文解释——展示具体记录和时间，向用户确认。
- **R-BS-05 时间精度**：日期精度可为准确日期、相对时间、区间或未知；相对日期按用户时区处理；录入时间和实际发生时间必须分开。
- **R-BS-06 用户怀疑与 AI 推测**：用户本人提出的怀疑（「我怀疑是偏头痛」）自动记录为用户假设（BodyHypothesis，来源为用户），不当作确诊；Agent 自己提出的假设只保留在分析过程与提案审计中，不写入 BodyState。
- **R-BS-07 事实与症状经历分离**：BodyFact 保留用户当时确切陈述及实际发生时间、来源和独立的更正/撤回记录状态；不使用统一的 active/resolved/historical 生命周期。SymptomEpisode 仅关联同一段症状经历的有效事实，依据实际症状时间线、关联和领域事件推导 unknown/ongoing/ended。改善、未继续报告或时间间隔不等于症状结束；明确结束后再次发生为关联旧经历的新 Episode。关联的 High 可自动处理，Medium/Low 不擅自确立身份；关键历史更正与 Episode 合并/拆分需要用户针对准确目标的授权。
- **R-BS-08 差异化事实类别与单一权威**：BodyFact 保留 symptom / health_history / activity / lifestyle / training_feedback 五类，各自具有适用的结构化属性和时间语义；既往事件、一次活动、持续习惯和训练反馈不强行共用症状生命周期。正式训练完成/跳过由 Trainer 日志权威持有；身体主观反应与明确症状按对应 BodyFact 记录并引用来源，不复制训练完成事实。
- **R-BS-09 来源分级的身体观察**：带来源和方法的自报测量、自测及设备观察可记录为 BodyObservation，并保留真实来源、原始值和单位；自报不自动成为临床核实数据。文件 OCR/解析候选必须满足已有证据管线准入后才可成为对应观察；文件准入状态、Observation 陈述有效性和医学证据等级相互独立，不因上传或自动提取形成 Diagnosis。
- **R-BS-10 主动澄清、回放与隐私边界**：遇到会影响病程判断的实质冲突，Agent 应优先在实时对话调用 ask_user，展示已有信息和明确选项，并允许自由解释；已明确的其他事实继续入库。交互未完成且冲突直接影响 Episode 状态时，投影可为 unknown 并保留冲突与先前依据；澄清交互状态属于 Chat，不是病程状态。业务有效时间与系统记录修订时间分离，纠错、撤回陈述、删除个人信息是三种不同操作；清除原始资料与已采纳衍生证据的执行规则仍待 DC-033/035，不能将软删除视为已完成隐私清除。

| 自然语言 | 预期处理 | 规则 |
| --- | --- | --- |
| 「我今天抬高右手时肩胛内侧酸痛」 | 保存本人右侧症状、动作触发和时间 | R-BS-01 |
| 「去年左臀疼，后来好了」 | 保存过去发生与恢复，当前不标记疼痛 | R-BS-04 |
| 「练完腿部后有点腿麻」 | 保存现象与时间关系，不自行判断病因 | R-BS-02 |
| 「我怀疑是偏头痛」 | 记录为用户提出的假设，不当作确诊 | R-BS-02、R-BS-06 |
| 「朋友最近肩膀痛」 | 不写入本人的身体状态 | R-GEN-01 |
| 「偏头痛有什么表现？」 | 作为普通知识咨询回答 | R-GEN-01 |

追问示例（R-BS-03）：

- 「你说的右肩是现在新出现的问题，还是想纠正之前的左肩记录？」
- 「你指的是哪个训练计划中的深蹲？」
- 「你说的头痛是你本人，还是你刚才提到的家人？」

### 2.3 Diagnosis 综合诊断

每个用户只有一份当前的 **Diagnosis**。每个 ConditionEntry 都是一项**具体、具名的医学疾病/综合征诊断结论**，可以处于疑似阶段，但不能用“抬手疼痛”等纯症状标题冒充病名；用户尚无足够证据形成具名诊断时，症状与不确定性继续留在 BodyState 或分析记录中。

- **R-DX-01 唯一聚合与独立诊断身份**：一份 Diagnosis 可以包含多个经用户采纳的 ConditionEntry，并保留 inactive 的历史条目。相同医学概念的证据修订保持 conditionId；实质不同的诊断概念新建 conditionId，即使引用同一 SymptomEpisode。局部更改不影响无关诊断；一次原子事务最多一个 DiagnosisRevision。不新增 BodyConcern，也不在 Diagnosis 重建症状 Episode。
- **R-DX-02 分析请求与采纳授权分离**：用户明确请求分析、局部更新或重新分析即授权创建正式 ConditionAnalysisRun，无需重复确认开始；普通聊天的初步讨论与 BodyState 的自动记录不是正式分析。**请求分析不等于采纳诊断。**
- **R-DX-03 完整诊断提案**：每个 create/update 提案明确医学名称、已获得的来源声明、支持/反对/背景证据、确定性与信息缺口、原因分析和处理建议。已有诊断的实质更新、诊断间关系和采纳状态变更都必须针对准确提案内容得到用户授权。
- **R-DX-04 用户仅决定采纳**：正式提案在 Chat 中供用户逐项 **采纳 / 不采纳 / 继续补充**；采纳不提高 AI 医学判断强度，也不能制造医生诊断或临床来源。拒绝新增提案不创建条目；拒绝已有诊断的更新/停用提案不改变原条目；明确撤回属于另一操作。不因拒绝就声称医学排除。对准确内容与证据版本的决定单独留档，无相关新证据不得重复打扰。
- **R-DX-05 只纳入已确认的具名诊断**：当前列表显示 adopted ConditionEntry；历史 inactive 可追溯。普通症状、用户尚未采纳的鉴别诊断和 AI 假设不混入正式列表；用户可采纳带有清楚不确定性说明的疑似诊断。
- **R-DX-06 新证据不自动修订诊断**：明确的新身体事实、Episode 改动与合格临床证据先写入其权威来源。Agent 可以自动做相关性检查、合并去重并建议复核，关键事实冲突可主动 Ask User；正式 Diagnosis 分析须由用户明确发起，诊断更新须再确认。复核提示不等于更改结论，也不建立独立 DiagnosisReviewTask。
- **R-DX-07 普通咨询与正式诊断分离**：一般知识解释、初步鉴别方向和普通知识问题不能直接创建 Diagnosis 条目；必要时建议专业医疗评估，不能将 AI 分析称为医生确诊。
- **R-DX-08 来源和确定程度各自独立**：AI 评估采用 suspected / likely 两个定性级别，解释判断依据和信息缺口，不给未经校准的百分比。用户采纳不决定级别。医疗文件、用户转述医生、用户本人怀疑、AI 分析分别保留可追溯来源声明；医生“考虑”与“明确诊断”按原始措辞展示。经准入但只有数值的报告不能冒充医生的具名诊断；临床来源条目无需虚构 AI 判断级别。
- **R-DX-09 当前结果为默认视图**：普通用户查看的是一份当前综合诊断，按条目展示医学名称、来源、证据边界、确定性/临床声明、处理建议及复核提示；inactive 历史可查，但不暴露内部技术修订号或报告版本切换器。
- **R-DX-10 不足与安全阻断**：证据不足不制造医学病名或虚假确定性；严重需停止分析的风险可在已展示提案后阻断整个 Run，先显示必要就医安全提示，停止后续确认，Run 的决定都不生效、Diagnosis 不修订；风险得到妥善处理后由用户发起新 Run。只影响 Trainer 的一般限制不自动终止诊断分析。
- **R-DX-11 不为凑字段而编造**：ConditionEntry 必须具名医学诊断；尚不能判断具体医学名称时返回 insufficient_evidence 并保留 BodyState 症状与 Run 的鉴别讨论。已有具名诊断的原因可明确“尚不明确”，处理方向可为观察、专业检查或就医，不强迫训练处方。
- **R-DX-12 逐项确认、整体一次提交**：一次 Run 可产生多个诊断提案，逐项采纳或拒绝。全部结算或用户明确结束本轮确认后，有效决定一次原子提交；补充证据后必须复核此前已决定提案，只有受影响者需要重新确认。关闭界面/中断不等于拒绝，pending 可恢复；无实际变化不产生空 Revision。
- **R-DX-13 用户直接更正与撤回**：用户明确要求纠正不影响医学身份的展示元数据、或从当前采纳中撤回准确的诊断时，经轻量确认后记录 ConditionDirectEdit 并生效；取消不改变 Diagnosis。Agent 不得通过直接编辑偷偷修改医学判断、来源、证据或处理建议。“右肩好了”等身体变化进入 BodyState，不再触发 ConditionEntry.mark_resolved。
- **R-DX-14 诊断关系与替代**：一条身体证据可用于多个诊断；支持、反对和背景证据分别记录。不同诊断可具有鉴别、替代或有依据的共存关系；采纳新诊断不自动停用旧诊断，更不等于旧诊断被医学排除。需要相应用户确认。
- **R-DX-15 Disposition 与历史**：ConditionEntry 的当前采纳状态仅 adopted / inactive；撤回、被新结论替代、不再适用和重新采纳的原因是独立历史决定事件。停用不删除事实或诊断历史；inactive 重新采纳需以当前证据重新分析并确认。
- **R-DX-16 临床声明并存**：不同医生/不同时点的诊断声明独立保存来源及原始不确定性，较新的文件不自动覆盖旧声明；冲突由 Agent 说明证据与局限，正式结论只能经用户确认修订。来源撤销时重新计算当前证据资格并提示复核，不无声改写历史。
- **R-DX-17 复核去重**：根据新证据及 Run 已评估范围派生 reviewRecommended，相关提醒合并；用户暂不处理只收起提示，有重要新证据可再次提醒；已评估内容不重复提醒，正式复核无变更时不创建 DiagnosisRevision。安全风险仍由 SafetyState 独立处理。

### 2.4 TrainingPlan 训练计划

- **R-TP-01 多份独立计划**：用户可以同时拥有多个计划，例如臀腿力量、肩胛控制和有氧训练。每份计划维护自己的动作、组次、频率、目标和训练记录；修改某份计划不影响其他计划。
- **R-TP-02 完整处方**：**每份 TrainingPlan 都是一套完整方案，而不是一个动作或训练部位模块**；动作按热身、正式训练、必要放松组织，明确动作名称、组数、次数/时长和训练频率。热身和放松按实际需求制定，不把示例动作当作所有人的默认处方。一份计划可以包含一次或多次课的模板（如 A/B 日），每次课模板各自按热身 → 正式训练 → 放松组织；计划中的「课模板」与实际执行的「训练记录」是两回事。
- **R-TP-03 用户主动修改**：例如「把臀腿计划里的深蹲替换掉」。目标明确、没有额外危险或歧义时，只改指定计划的相关内容，不重复征求形式化确认；范围不清或影响重大时先澄清。
- **R-TP-04 Agent 建议需用户接受**：例如用户新报告腿部麻木，Agent 发现现有臀腿训练可能受影响，应说明影响和建议，并通过交互工具让用户选择「接受调整 / 暂不修改」。用户未接受时，所有训练计划内容保持不变。关闭界面不等于拒绝，建议保持待决定、可以回来继续；明确选择「暂不修改」才算拒绝；超时或计划已被其他修改改变时建议失效。
- **R-TP-05 不自动改计划**：无论 BodyState、Diagnosis 或训练记录如何变化，均不自动修改已接受的计划内容。

### 2.5 训练执行与反馈

- **R-EX-01**：用户可以打开某份计划进入 Trainer 训练、记录完成情况与主观反馈；明确的身体变化按 R-BS-01 进入 BodyState。
- **R-EX-02**：动作示范、训练前后的时间关系、3D 人体模型不能单独证明病因或疗效。
- **R-EX-03 执行界面**：Trainer 针对指定计划的某次课，显示当前动作、当前组次与目标次数/时长，提供计时；支持暂停与恢复、跳过动作。
- **R-EX-04 真实完成情况**：训练记录按计划、日期和动作定位，只记录用户明确完成或跳过的内容；不根据点击、浏览或动作演示推断已完成。

### 2.6 Person 个人档案与当前状态

- **R-PS-01**：Person 负责展示用户当前资料及其身体记录、资料、器材等。Diagnosis 呈现当前病情集合，TrainingPlan 显示每份计划当前生效内容。
- **R-PS-02**：用户不需要知道 BodyState、Diagnosis 或计划的内部修订编号。
- **R-PS-03 上传资料与文件证据**：用户上传的照片、报告等资料归属 Person 的 Media / Reports；基于资料的分析在 Chat 中发起，不设独立的「上传 → 结果」流程。文件证据沿用 [健康文件证据管线](../architecture/health-document-evidence-pipeline.md) 与 [ADR 0013](../adr/0013-adopt-versioned-health-document-evidence-pipeline.md) 的既有规则（来源可追溯、分级自动采纳、人工核实、机制版本化），本文件不另立识别流程：
  - 路径为：原始文件 → 抽取 → 证据采纳 → BodyObservation / Diagnosis 分析；
  - 可靠的抽取结果可按上述规则自动采纳；存疑结果等待用户核实；
  - 未经核实或低于阈值的结果不得作为可信的临床证据；
  - 自动采纳的数值不会自动形成任何诊断，进入 Diagnosis 仍需正式分析与用户确认（R-DX-02～04）。
- **R-PS-04 身份信息位置**：Person 保留五个分类标签页（Records、Equipment、Media、Reports、Habits）；身份等基础资料显示在 Person 窗口标题区，并通过身份弹层（Identity Popover）查看和编辑，不另设第六个标签页。
- **R-PS-05 Habits 与 Records 写入权威**：明确的本人生活习惯和身体记录遵循 R-BS-01 的自动入库原则，仅关键歧义或特定来源证据准入按原领域规则处理；Person 负责展示、录入和更正入口，不复制 BodyState/Diagnosis 权威数据。通过 Person 修改也必须由各权威领域完成校验与持久化；Diagnosis 的结论确认不能借由 Records 自动入库规则绕过。

### 2.7 安全

- **R-SAFE-01**：出现需要就医检查的警示情况时，清楚提示下一步，可以提醒、限制不安全的训练执行或建议专业帮助。
- **R-SAFE-02**：执行保护与计划内容修订是两件事；不能借安全提示静默改写动作、强度或排程。
- **R-SAFE-03 风险状态与执行门禁**：风险状态以 BodyState 的安全状态为准，记录风险等级、作用范围（整份计划或具体动作）、有效期与解除条件；Trainer 在执行前和执行中据此把关。计划本身的状态不因此改变，界面单独显示「暂不宜执行」及原因。
- **R-SAFE-04 解除限制**：每条限制有一种解除方式——到期自动解除、用户复核、专业人员放行。只有「到期自动解除」的限制在有效期结束时自动解除；其他限制到期只提醒复核，在用户通过复核重新确认症状，或记录专业人员（如医生）的放行及来源之前，继续生效。需要就医检查的警示情况默认需要专业人员放行。Agent 不能自行解除限制。

## 3. 全局业务约束

- **G-01**：同一用户只有一份 BodyState、一份当前综合 Diagnosis，可以有多份 TrainingPlan。
- **G-02**：Conversation 是交流与操作通道，不是唯一的身体状态存储。
- **G-03**：身体事实、客观观察、模型假设和医疗结论必须具有不同的认知与权限语义。
- **G-04**：用户的健康信息必须保证归属、授权、来源和可更正性。
- **G-05**：安全规则高于普通解释与训练执行。
- **G-06**：用户不必通过固定的线性流程才能使用产品。
- **G-07**：Agent 修改训练内容必须有可验证的用户授权。
- **G-08**：内部修订不可随意改写历史；用户默认只看到当前结果。

## 4. 典型用户场景

| 场景 | 过程与预期 | 规则 |
| --- | --- | --- |
| **A｜自动记录** | 「昨天久坐后左臀很酸，今天好多了。」→ 写入两个时间状态，不追问无意义的问题，不自动改训练 | R-BS-01、R-BS-04、R-TP-05 |
| **B｜纠错** | 「之前说右肩疼是口误，其实是左肩；最近右肩也疼。」→ 修正错误记录、保留确实发生过的左肩问题、创建最近右肩问题 | R-BS-04 |
| **C｜综合更新** | 当前有 A、B、C 三个病情，用户请求重新分析 B → 用户在确认工具中选择后 B 更新，A/C 原样保留，整体 Diagnosis 修订一次 | R-DX-01～04 |
| **D｜计划建议** | 用户新报告腿麻，臀腿计划可能不适合 → Agent 提示并询问；暂不修改时计划保持不变，接受后仅修改该计划 | R-TP-04 |
| **E｜普通咨询** | 「偏头痛是什么？」→ 提供解释，不创建本人的偏头痛病情 | R-GEN-01、R-DX-07 |
| **F｜风险阻断** | 出现需要就医检查的警示情况 → 清楚提示下一步，限制不合适的训练执行，保留原计划内容 | R-SAFE-01～02 |

未决问题与已发现的规格矛盾集中列于 [开放问题](./open-questions.md)。

## 5. 领域状态契约落地边界

每个领域的字段、状态枚举、合法转移、事件、权限、历史与验收以 [领域契约](./domain/README.md) 中相应权威文档为准。不得把 BodyHypothesis 与 Agent 推测、TrainingPlan.status 与 SafetyRestriction、训练结束与全部动作已完成、Person 展示与第二份身体真值混同。

未定的业务语义在 [domain-decisions.md](./domain-decisions.md) 中保留，现阶段只覆盖可核实子集；现有代码与目标差异见 [implementation-gaps.md](./implementation-gaps.md)，不代表已经实现。
