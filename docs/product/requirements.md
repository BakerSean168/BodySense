# BodySense · 产品需求规格

**状态：产品业务规格 · 2026-10-11**

## 1. 产品目标

BodySense 面向希望了解身体不适、体态、活动能力及训练情况的人群。用户可以自然描述身体变化，按需获取综合诊断分析，管理多份训练计划，并持续记录训练反馈；不需要理解内部 Agent 运行、对象修订或医学术语。

## 2. 业务流程

### 2.1 普通知识咨询

用户提问一般健康知识、训练方法或讨论他人问题时，Agent 直接解释。知识问题、假设案例及第三人症状不自动写入本人的 BodyState。

### 2.2 BodyState：自动积累本人身体信息

当用户清晰表达自己的身体状态，Agent 直接提取并写入，**无需逐条确认**。

| 自然语言 | 预期处理 |
| --- | --- |
| 「我今天抬高右手时肩胛内侧酸痛」 | 保存本人右侧症状、动作触发和时间 |
| 「去年左臀疼，后来好了」 | 保存过去发生与恢复，当前不标记疼痛 |
| 「练完腿部后有点腿麻」 | 保存现象与时间关系，不自行判断病因 |
| 「我怀疑是偏头痛」 | 记录用户提出的可能性，不当作确诊 |
| 「朋友最近肩膀痛」 | 不写入本人的身体档案 |
| 「偏头痛有什么表现？」 | 作为普通知识咨询回答 |

必要条件：本人归属明确、语义可确定、时间不被虚构、来源可追踪。不能因 Agent 生成了某种医学推测就把推测写成用户事实。

### 2.3 有歧义才确认

仅当主体、身体部位、左右侧、发生时间、历史记录性质或执行对象不能明确时使用交互工具追问。Agent 应定位具体问题：

- 「你说的右肩是现在新出现的问题，还是想纠正之前的左肩记录？」
- 「你指的是哪个训练计划中的深蹲？」
- 「你说的头痛是你本人，还是你刚才提到的家人？」

同一消息中可确定的其他事实照常记录，不因一处模糊而整体阻塞。

### 2.4 时间与冲突

- **真实发展**：「之前左臀痛，现在好了」——保留真实病程，更新当前状态。
- **记录更正**：「之前说左肩是口误，其实是右肩」——更正错误来源，不虚构病情迁移。
- **重复**：对同一事件再次描述——去重或增加来源，不生成无意义副本。
- **真正冲突**：同一时间、同一条件下状态互斥，且无法用上下文解释——展示具体记录和时间，向用户确认。

日期精度可为准确日期、相对时间、区间或未知；相对日期按用户时区处理。录入时间和实际发生时间必须分开。

### 2.5 Diagnosis：唯一当前综合诊断

每位用户只有一份当前的综合 **Diagnosis**，内部包含多个稳定身份的病情条目。它不是每次问诊重新建立的一份报告。

- 单个病情可独立分析、更新、标记缓解或不再适用。
- 一次正式分析可同时更新多个关联病情。
- 不相关病情条目原样保留；一次原子更新生成一个整体 Diagnosis 修订。
- 用户在 Chat 中提出「分析一下我的右肩」「更新综合诊断」即授权开始正式分析，但**不代表直接接受 AI 的分析结论**。
- 每个正式病情必须包含**明确名称、原因分析、处理方案**；Agent 将这些内容作为一个完整提案，通过 Chat 内的确认工具让用户核对后才能纳入或实质更新 Diagnosis。
- Agent 可以提出应当重新分析的建议，但不能未经用户请求/授权就发布新的正式 Diagnosis。
- 普通 Chat 可以讨论初步可能方向，不等于已经产生正式诊断。
- 无足够证据的症状、原因或问题保留在 BodyState/分析提案，**不混入已确认 Diagnosis 病情列表**；不能因为报告需要完整就制造病名。
- 用户转述医生诊断、可核验临床材料、用户的自行猜测、Agent 的病因可能性是不同类型的证据和结论，不能混同。

用户查看一份当前综合判断，按病情展开具体内容及依据，不显示技术版本号或报告版本切换器。病情真实变化和必要的证据来源仍可追踪。

### 2.6 TrainingPlan：多份计划，独立更新

用户可以同时拥有多个计划，例如臀腿力量、肩胛控制和有氧训练。每份计划维护自己的动作、组次、频率、目标和训练记录。**每份 TrainingPlan 都是一套完整方案，而不是一个动作或训练部位模块**；具体动作按热身、正式训练、必要放松组织，明确动作名称、组数、次数/时长和训练频率。

**用户主动修改**：例如「把臀腿计划里的深蹲替换掉」。目标明确、没有额外危险或歧义时，可只改指定计划的相关内容，不重复征求形式化确认。

**Agent 主动建议**：例如用户新报告腿部麻木，Agent 发现现有臀腿训练可能受影响。Agent 应说明影响和建议，并通过交互工具让用户选择是否调整。用户未同意时，所有训练计划内容保持不变。

无论 BodyState、Diagnosis 或训练日志如何变化，均不自动修改已接受计划内容。

**安全保护**：当现有计划可能带来明显风险，系统可以提醒、限制不安全的训练执行或建议专业帮助。执行保护与计划内容修订是两件事；不能借安全提示静默改写动作、强度或排程。

### 2.7 执行与反馈

用户可以打开某份计划进入训练模式、记录完成情况与主观反馈；明确的身体变化进入 BodyState。动作示范、训练前后时间关系、3D 人体模型不能单独证明病因或疗效。

### 2.8 Person 与当前状态

Person/Profile 负责展示用户当前资料及其身体记录、资料、器材等。Diagnosis 呈现当前病情集合，Training 显示每份计划当前生效内容。用户不需要知道 BodyState、Diagnosis 或计划的内部修订编号。

## 3. 全局业务约束

1. 同一用户只有一份 BodyState、一份当前综合 Diagnosis，可以有多份 TrainingPlan。
2. Conversation 是交流与操作通道，不是唯一的身体状态存储。
3. 身体事实、客观观察、模型假设和医疗结论必须具有不同的认知与权限语义。
4. 用户的健康信息必须保证归属、授权、来源和可更正性。
5. 安全规则高于普通解释与训练执行。
6. 用户不必通过固定的线性问诊流程才能使用产品。
7. Agent 修改训练内容必须有可验证的用户授权。
8. 内部修订不可随意改写历史；用户默认只看到当前结果。

## 4. 典型用户场景

**A｜自动记录**：「昨天久坐后左臀很酸，今天好多了。」→ 写入两个时间状态，不追问无意义的问题，不自动改训练。

**B｜纠错**：「之前说右肩疼是口误，其实是左肩；最近右肩也疼。」→ 修正错误记录、保留确实发生过的左肩问题、创建最近右肩问题。

**C｜综合更新**：当前有 A、B、C 三个病情，用户请求重评估 B → B 更新，A/C 原样保留，整体 Diagnosis 修订一次。

**D｜计划建议**：用户新报告腿麻，臀腿计划可能不适合 → Agent 提示并询问；拒绝时计划保持不变，同意后仅针对该计划作修改。

**E｜普通咨询**：「偏头痛是什么？」→ 提供解释，不创建本人的偏头痛病情。

**F｜风险阻断**：出现需要专业评估的警示情况 → 清楚提示下一步，限制不合适的训练执行，保留原计划内容。
