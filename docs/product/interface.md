# BodySense · UI 与交互规格

## 1. 核心空间

产品的空间由三层协作：

~~~text
交互工具层：人体点选 / 涂抹 / 动作查看 / 临时确认
业务窗口层：Chat · Person · Diagnosis · TrainingPlan · Trainer
底层桌面：持续存在的可交互 3D 人体 Canvas
~~~

3D 人体是持久空间场景；用户移动、收起或关闭业务窗口即可查看人体，不需要先进入一个人体页面。Chat 是自然交流与操作意图入口，不要求永久占据固定左侧或另一侧业务分屏。业务窗口可按任务独立打开，支持合理的拖动、收起、聚焦与恢复。

窗口打开/关闭或工具模式切换不应丢失：
- 当前聊天、等待回答的交互工具及其恢复状态；
- 当前选中的身体部位和区域上下文；
- 打开的业务对象与未完成操作；
- 当前训练计划的准确身份和用户授权状态。

## 2. 主要窗口

| 窗口 | 默认内容 | 主要动作 |
| --- | --- | --- |
| Chat | 对话、简短的已保存反馈、追问、建议和批准控件 | 描述身体、提问、正式分析请求、计划调整请求 |
| Person / Profile | 当前个人资料、身体记录、器材和相关个人资产 | 查看、纠正、补充、管理个人资料 |
| Diagnosis | 唯一当前综合分析，按病情独立展开 | 查看依据、补充信息、从 Chat 请求局部重评估 |
| TrainingPlan | 该计划当前已接受动作/强度/频率/安排 | 查看、请求局部修改、接受或拒绝建议 |
| Trainer | 当前计划的执行任务和动作演示 | 执行/暂停/跳过、记录反馈、查看安全约束 |

组件的布局、间距、动效和层级应与 Penpot 的实际可编辑组件保持一致。本文件定义数据与交互语义，不规定另一套视觉样式。

## 3. Person / Profile

参考 Penpot 的 Person/Profile 原型，并保留其既定分类：**Records、Equipment、Media、Reports、Habits**。

- Records 展示当前可用的身体记录；缺数据时使用明确的空状态，可继续补充。
- Equipment 展示已添加器材，数量按数据自然变化。
- Media / Reports 保留资料、来源、处理与核实状态。
- Habits 提供具有时间语义的生活习惯信息。
- 个人身份信息与身体状态由各自权威数据源提供，不采用演示值作为真实资料。

Person 不是内部 Revision 管理器，不展示 BodyState 技术修订号。

## 4. Diagnosis

Diagnosis 始终展示**当前唯一的综合结果**：

- 病情条目按稳定身份组织；同一病情更新后保持可识别。
- **当前综合诊断只列出已通过确认流程的病情**。每条卡片完整展示病情名称、原因分析及处理方案；用户能查看确认来源与证据边界。未确认的症状及可能病因不属于该列表。
- Chat 中的病情确认工具需要先展示完整提案，再由用户选择确认纳入/继续补充；确认后才更新诊断窗口。
- 病情当前状态、证据与不确定性分开表达。
- 涉及多个病情的分析一次更新后应一起生效。
- 不足以判断时显示待明确的信息，不能在 UI 中营造医学确定性。
- 用户能自然发起「帮我重新分析这个问题」，由 Chat/业务操作完成。
- 不出现技术版本号、历史版本列表、版本选择器或「局部独立诊断报告」。

真正的身体变化历史可以在记录详情中查看，与技术修订不混为一谈。

## 5. TrainingPlan

每份计划显示自己的当前已接受内容。**展示单位是完整计划，而不是若干部位或抽象训练模块卡片**：包括计划目标和频率，以及按顺序排列的热身、正式训练、必要放松；每个动作都要显示名称、组数、次数/时长。修改某个动作时只更新所属计划，不会使其他计划的窗口内容变化。

Agent 主动建议调整时，Chat 的轻量交互呈现：
1. **影响哪个计划**、受影响的具体动作；
2. **为什么建议复核**及必要的安全提示；
3. **调整前后是什么**，不隐藏重要变更；
4. **接受调整 / 暂不修改** 两项明确结果。

复杂变更可在同一计划窗口中展开审阅；只有接受/明确请求后才更新计划内容。拒绝或关闭不造成暗改。

## 6. 人体交互工具

当 Agent 需要用户指定位置时，允许临时开启点选或涂抹工具，用户在底层人体上完成定位，交互工具将部位和其他用户明确提供的信息返回到原会话。

**选择部位并不自动意味着存在疼痛、异常或临床检查结果。** Agent 需要用户描述现象，才能按 BodyState 规则记录。动作示范属于参考素材，不自行推断用户真实姿态或负荷。

## 7. 平台与辅助功能

- **桌面**：支持多业务浮动窗口，可利用屏幕空间保留可见的人体桌面。必须按实际 Viewer 可见区域验证最小支持窗口宽度，不能仅在 1440px 主画板内验证；标题、卡片与按钮不得横向裁切。
- **窄屏/移动端**：同一业务语义使用适合屏宽的单任务窗口、覆盖层或底部表单；底层人体状态和任务上下文保持可恢复。
- **交互**：Esc 关闭顶层窗口或工具而不丢数据；明确的键盘焦点和返回路径；支持键盘操作和文本部位选择。
- **权限与状态**：加载、错误、未提交、待确认、安全阻断均有可理解反馈；颜色不是状态的唯一表达方式。
