# BodySense · UI 与交互规格

**本文件定义窗口、交互与平台要求。** 业务规则见 [产品需求](./requirements.md)，数据见 [领域模型](./domain.md)，Agent 流程见 [Agent 工作流](./agent-workflows.md)。视觉基准是 Penpot 文件 **BodySense · Product Design** 的 Product 页（见 §8）；设计稿中的旧窗口名按 [术语表 §3](./glossary.md#3-penpot--旧代码名称对照) 换算。

## 1. 核心空间

~~~text
交互工具层：人体点选 / 涂抹 / 动作查看 / 临时确认
业务窗口层：Chat · Person · Diagnosis · TrainingPlan · Trainer
底层桌面：持续存在的可交互 3D 人体 Canvas
~~~

3D 人体是持久空间场景；用户移动、收起或关闭业务窗口即可查看人体，不需要先进入一个人体页面。Chat 是自然交流与操作意图入口，不要求永久占据固定左侧或另一侧业务分屏。业务窗口可按任务独立打开，支持合理的拖动、收起、聚焦与恢复。

窗口打开/关闭或工具模式切换不应丢失：

- 当前聊天、等待回答的交互工具及其恢复状态；
- 当前选中的身体部位和区域上下文；
- 打开的业务对象与未完成操作；
- 当前训练计划的准确身份和用户授权状态。

## 2. 业务窗口

| 窗口（Penpot 旧名） | 默认内容 | 主要动作 |
| --- | --- | --- |
| Chat（Assistant） | 对话、简短的已保存反馈、追问、建议和批准控件 | 描述身体、提问、发起正式分析、请求计划调整 |
| Person（Profile） | 当前基础资料、身体记录、器材和相关个人资产 | 查看、纠正、补充、管理个人资料 |
| Diagnosis（Assessment） | 唯一当前综合诊断，按病情独立展开 | 查看依据、补充信息、从 Chat 请求局部重新分析 |
| TrainingPlan（Training） | 该计划当前已接受的动作/强度/频率/安排 | 查看、请求局部修改、接受或暂不采纳建议 |
| Trainer（Workflow/Training） | 当前计划某次课的执行：当前动作、组次、计时与动作演示（§5.1） | 开始/暂停/恢复/跳过、记录完成与反馈、查看安全约束 |

组件的布局、间距、动效和层级与 Penpot 的实际可编辑组件保持一致。本文件定义数据与交互语义，不规定另一套视觉样式。

## 3. Person 个人档案

参考 Penpot 的 Profile 原型，保留其既定的五个分类标签页：**Records、Equipment、Media、Reports、Habits**（R-PS-04）。身份等基础资料（Profile 领域对象）显示在窗口标题区，点击后以 Identity Popover 查看和编辑，不作为第六个标签页。

- Records 展示当前可用的身体记录；缺数据时使用明确的空状态，可继续补充。
- Equipment 展示已添加器材，数量按数据自然变化。
- Media / Reports 保留资料、来源、处理与核实状态。用户上传的照片、报告等资料归入这里；基于资料的分析在 Chat 中发起（Penpot 中 Workflow/Assessment 的「上传 → 证据 → 结果」流程为旧流程，不再采用）。识别值区分已采纳、待用户核实、未采纳三种状态（对应证据管线的 admissible / needs_review / rejected），待核实值需展示来源位置供用户核对、更正或否定；未采纳的值不显示为可信证据（R-PS-03）。
- Habits 提供具有时间语义的生活习惯信息。
- 基础资料与身体状态由各自权威数据源提供，不采用演示值作为真实资料。
- Person 不是内部修订管理器，不展示 BodyState 技术修订号（R-PS-02）。

## 4. Diagnosis

Diagnosis 始终展示**当前唯一的综合结果**（R-DX-01、R-DX-05、R-DX-09）：

- 病情条目按稳定身份组织；同一病情更新后保持可识别。
- 当前列表只列出用户采纳中的病情（`disposition = adopted`）。结论标签：「大概率是」「疑似 · 你选择保留」「临床诊断」；来源单独标注（临床文件 / 你转述的医生诊断 / Agent 分析 / 你的怀疑），「你转述的医生诊断」不得显示为有文件支持。标签用文字加图标区分（不只靠颜色）。
- 用户撤回或不再适用的条目不作为当前病情显示，但在记录详情中可追溯（R-DX-01）。
- 每条卡片完整展示病情名称、原因分析及处理方案；名称可为描述性健康问题，原因可显示「原因不明 / 证据不足」，处理方案可为观察、检查或就医（R-DX-11）；疑似条目额外列出待明确的信息；用户能查看确认来源与证据边界。
- 病情当前状态、证据与不确定性分开表达；不足以判断时显示待明确的信息，不在 UI 中营造医学确定性。
- 涉及多个病情的一次更新在窗口中一起生效。
- 用户能自然发起「帮我重新分析这个问题」，由 Chat / 业务操作完成。
- 不出现技术版本号、历史版本列表、版本选择器或「局部独立诊断报告」。真正的身体变化历史可以在记录详情中查看，与技术修订不混为一谈。
- 安全阻断状态（Penpot：Workflow/Assessment Safety Hold）保留，用于展示阻断原因与就医提示。

**Chat 中的病情确认工具**（confirm_condition）：

- 先展示完整病情提案：名称、原因、处理方案、来源、证据边界；
- Agent 分析 / 用户怀疑来源的提案提供四个结果互不相同的操作：「大概率是这个」「可能是，先保留」「不是这个」「继续补充」；「大概率是这个」附近说明这不是临床诊断；
- 临床来源的提案提供「纳入我的病情管理」「不纳入」「继续补充」（具体文案待 Penpot 核对，见 [Q-19](./open-questions.md)）；
- 一次分析有多个提案时逐个展示、逐个决定；全部结算后 Diagnosis 窗口中的变化一起生效（R-DX-12）；
- 关闭 Chat 或离开后再回来，未决定的提案仍可继续选择；已作出的决定显示为已选择但尚未生效；
- 提交成功前不得显示为已写入。

## 5. TrainingPlan

每份计划显示自己的当前已接受内容。**展示单位是完整计划，而不是若干部位或抽象训练模块卡片**（R-TP-02）：包括计划目标和频率，以及按顺序排列的热身、正式训练、必要放松；每个动作显示名称、组数、次数/时长。修改某个动作时只更新所属计划，其他计划的窗口内容不变。

Agent 主动建议调整时，Chat 的轻量交互呈现：

1. **影响哪个计划**、受影响的具体动作；
2. **为什么建议复核**及必要的安全提示；
3. **调整前后是什么**，不隐藏重要变更；
4. **接受调整 / 暂不修改** 两项明确结果。

复杂变更可在同一计划窗口中展开审阅；只有接受或明确请求后才更新计划内容，暂不修改或关闭不造成暗改。关闭后建议仍为待决定，可在 Chat 中回到该建议继续选择；建议失效时明确提示原因。

计划有多个课模板（如 A/B 日）时分别展示，每个模板内按热身 → 正式训练 → 放松排列。存在有效的安全限制时，计划窗口与 Trainer 显示「暂不宜执行」及原因、作用范围、解除条件；计划状态与内容不变（R-SAFE-03）。

### 5.1 Trainer 训练执行

规则见 R-EX-01～04、R-SAFE-03。

- 打开指定计划的指定课模板；显示当前动作、第几组 / 共几组、目标次数或时长、休息计时与动作演示。
- 支持开始、暂停、恢复、跳过当前动作；暂停后恢复回到原动作与组次，关闭窗口不丢失进行中的记录。
- 完成以用户的明确操作或陈述为准；浏览、点击动作卡片或播放演示不记为完成。
- 训练结束时可记录主观反馈；明确的身体变化按 R-BS-01 写入 BodyState。
- 受安全限制的动作或计划不可开始，显示「暂不宜执行」；只限制具体动作时，其余动作可继续。
- Penpot 中 Workflow/Training Today / Move / Feedback / Paused / Completed 对应上述执行状态；**Draft 状态保留**，其含义待 Penpot 核对（[Q-15](./open-questions.md)）。

## 6. 人体交互工具

当 Agent 需要用户指定位置时，允许临时开启点选或涂抹工具，用户在底层人体上完成定位，交互工具将部位和其他用户明确提供的信息返回到原对话。

**选择部位并不自动意味着存在疼痛、异常或临床检查结果。** Agent 需要用户描述现象，才能按 R-BS-01 记录。动作示范属于参考素材，不推断用户真实姿态或负荷（R-EX-02）。

## 7. 平台与辅助功能

- **桌面**：支持多业务浮动窗口，保留可见的人体桌面。必须按实际 Viewer 可见区域验证最小支持窗口宽度，不能仅在 1440px 主画板内验证；标题、卡片与按钮不得横向裁切。
- **窄屏/移动端**：同一业务语义使用适合屏宽的单任务窗口、覆盖层或底部表单；底层人体状态和任务上下文保持可恢复。
- **交互**：Esc 关闭顶层窗口或工具而不丢数据；明确的键盘焦点和返回路径；支持键盘操作和文本部位选择。
- **状态反馈**：加载、错误、未提交、待确认、安全阻断均有可理解反馈；颜色不是状态的唯一表达方式。
