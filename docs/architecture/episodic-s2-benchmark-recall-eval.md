# 情景记忆 S2 基准与 S4 召回评测

> 状态：测量报告（供产品与隐私负责人定保留政策；不改变任何默认值）
> 关联：#515（S2 影子生成基准）、#517（S4 召回评测基线）
> 数据：全部为种子化合成语料，不含任何真实用户数据
> 代码：`apps/api/benchmarks/episodic/`，结果：`results/benchmark.json`
> 运行环境：PostgreSQL 18.6（一次性容器）、`pg_trgm` 1.6、迁移 `000001`–`000006`
> 对应提交：`66867f51`（基准实现），本报告随后的提交只含文档与结果

## 1. 结论摘要

1. **保留上限建议 96 条 / 32,000 字符作为默认候选。** 12 个月后保留 712/873 条
   （81.6%），等效记忆视界约 10 个月；存储约 24.9 KB 文本/用户（最大 32.0 KB）；
   prune p95 约 10.0 ms。
2. **48 条 / 16,000 字符不足以支撑“长期记得”的产品承诺。** 12 个月滚出 59.3%，
   等效记忆视界约 5 个月，且长笔记用户先被字符上限截断。
3. **200 条 / 64,000 字符可完整保留 12 个月**（零滚出），代价是保留面翻倍；
   只有在产品明确承诺超过 12 个月记忆时才建议采用。
4. **prune 延迟不是瓶颈。** 所有档位、两组模式下 p95 均 ≤ 11.4 ms，远低于 ADR 的
   ≤ 2 s 门；新增笔记工作相对无提炼只增加约 5–6 ms。
5. **规定的关键词路径（原生 FTS + ts_rank_cd + pg_trgm）在中文上不达标**：
   `recall@8` 0.6094、改写片 0.4455。原因是 PostgreSQL 没有中文分词，三字
   `pg_trgm` 对两字词无重叠；42.5% 的查询对全部候选的相似度都是 0，排序退化为
   按时间倒序。
6. **加入评测专用字符二元组对照后**，关键词 `recall@8` 为 0.8688、改写片 0.8000，
   **未触发**向量门 1（<0.85 或改写片 <0.75）。因此当前不建议启用向量；但 S4
   必须使用中文可用的关键词匹配，不能直接上线原生 `to_tsvector('simple')` /
   三字 `pg_trgm`。

## 2. 方法与边界

- **语料**：固定种子 `20261105`，8 个合成用户、52 周、每周 3 个对话片段，共
  1,248 个片段、4,992 条消息。类别按固定轮转混合：生活经历叙事、回复风格偏好、
  临床语句。临床片段**不生成笔记**，按 S2-A 的临床排除规则记为“生成缺口”
  （375 个），与“上限滚出”分开统计。
- **留存模拟**：按周推进，每个用户每周一个 prune 事务（删除该周原始消息、推进
  `pruned_through_seq` / `context_start_seq`）；启用提炼时在同一事务内按 S2-A
  的规则写入一条 `shadow` 笔记，并执行与运行时一致的最旧优先滚动（条数 + 字符
  两个上限，按 rune 计数）。写入的 `episodic_notes` 使用真实表、真实约束。
- **提炼桩**：确定性文本生成，不调用任何模型；因此延迟**不含**模型推理成本。
  这是有意的：本报告测量的是“清理 + 落库”的数据库成本，模型生成应异步/尽力而为。
- **可信度校验**：Go 内存滚动模拟与 PostgreSQL 实测的留存条数逐档完全一致；
  不一致时 harness 直接失败。
- **召回**：320 条中文查询（100 原词命中 / 110 改写同义 / 110 时间指代），每条
  标注应召回的笔记 id；查询在所属用户范围内检索 `episodic_notes`。检索只存在于
  评测代码，不新增 API 或运行时路径。
- **隔离**：一次性 PG18 容器（独立端口、独立库），跑完即删；不接 staging、
  生产、真实 Supabase，不读真实用户数据，不调用真实模型。

## 3. 留存、字符与被滚出比例

12 个月后（全部为合成数据）的实际留存：

| 上限（条 / 字符） | 留存笔记 | 留存字符 | 每用户均值 | 每用户最大值 | 滚出 | 滚出比例 | 主要约束 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 48 / 16,000（test-only） | 355 | 99,087 | 44.4 条 / 12.4 KB | 48 条 / 16.0 KB | 518 | **59.3%** | 混合：长笔记用户先撞字符，短笔记用户先撞条数 |
| 96 / 32,000（候选 A） | 712 | 199,010 | 89.0 条 / 24.9 KB | 96 条 / 32.0 KB | 161 | **18.4%** | 混合：长笔记用户字符满，短笔记用户条数满 |
| 200 / 64,000（候选 B） | 873 | 251,880 | 109.1 条 / 31.5 KB | 111 条 / 43.5 KB | 0 | **0%** | 无约束 |

逐用户明细（档位 = 条数 / 字符）：

| 用户 | 48 / 16,000 | 96 / 32,000 | 200 / 64,000 |
| --- | --- | --- | --- |
| 0（长） | 40 条 / 15,637（字符） | 81 条 / 31,650（字符） | 111 条 / 43,506 |
| 1（长） | 41 条 / 15,996（字符） | 82 条 / 31,986（字符） | 111 条 / 43,139 |
| 2（长） | 41 条 / 15,756（字符） | 82 条 / 31,607（字符） | 110 条 / 42,253 |
| 3（长） | 41 条 / 15,901（字符） | 83 条 / 31,829（字符） | 109 条 / 41,885 |
| 4（短） | 48 条 / 8,946（条数） | 96 条 / 18,071（条数） | 108 条 / 20,366 |
| 5（短） | 48 条 / 8,964（条数） | 96 条 / 17,954（条数） | 108 条 / 20,273 |
| 6（短） | 48 条 / 9,022（条数） | 96 条 / 17,989（条数） | 108 条 / 20,215 |
| 7（短） | 48 条 / 8,865（条数） | 96 条 / 17,924（条数） | 108 条 / 20,243 |

**读法**：

- 当前 48 / 16,000 的组合对长笔记用户是字符先满、对短笔记用户是条数先满，
  两类用户的实际记忆视界都只有约 **5 个月**。
- 96 / 32,000 把视界拉到约 **10 个月**；长笔记用户仍由字符约束（81–83 条），
  短笔记用户由条数约束（96 条、仅约 18 KB），字符上限对短笔记用户有约 14 KB 空余。
  若产品希望两类用户视界一致，可考虑 120 条 / 32,000 字符；本报告只测量了给定三档。
- 200 / 64,000 在 12 个月内不滚出；文本量仍很小（最大 43.5 KB/用户），但保留面、
  擦除面和隐私暴露面随之翻倍。

## 4. prune 延迟

每个用户每周一次 prune 事务，共 416 个样本/档/模式；“有提炼桩”包含笔记生成桩、
上限滚动与落库，但不含模型推理。

| 上限 | 模式 | p50 | p95 | max | 含笔记的 prune p95 |
| --- | --- | --- | --- | --- | --- |
| 48 / 16,000 | 无提炼 | 3.696 ms | 4.704 ms | 9.189 ms | — |
| 48 / 16,000 | 有提炼桩 | 7.075 ms | 9.831 ms | 22.066 ms | 9.956 ms |
| 96 / 32,000 | 无提炼 | 3.674 ms | 4.603 ms | 7.479 ms | — |
| 96 / 32,000 | 有提炼桩 | 6.624 ms | 10.024 ms | 21.423 ms | 10.030 ms |
| 200 / 64,000 | 无提炼 | 3.806 ms | 4.536 ms | 6.607 ms | — |
| 200 / 64,000 | 有提炼桩 | 7.597 ms | 11.311 ms | 19.139 ms | 11.497 ms |

结论：即使 200 条上限，prune p95 也在 11.4 ms；ADR 的 ≤ 2 s 门有约两个数量级
余量。增量主要来自每次写入时读取全部旧笔记做滚动，随上限近似线性增长，但在
200 条规模下仍可忽略。

## 5. 召回评测（recall@8）

同一 320 条标注查询，在每档上限的留存状态上评测；所有查询的目标笔记都被三档保留，
因此三档的召回数值相同，差别只体现在候选集大小与查询延迟。

| 指标 | 整体 | 原词命中 | 改写同义 | 时间指代 |
| --- | --- | --- | --- | --- |
| 规定路径（FTS OR + ts_rank_cd + pg_trgm 兜底） | **0.6094** | 0.9600 | **0.4455** | 0.4545 |
| 其中仅 FTS（原生 `simple` 配置） | 0.1125 | 0.3600 | 0.0000 | 0.0000 |
| 评测专用字符二元组对照 | **0.8688** | 1.0000 | **0.8000** | 0.8182 |

辅助观测：

| 项 | 48 / 16,000 | 96 / 32,000 | 200 / 64,000 |
| --- | --- | --- | --- |
| FTS 有命中的查询 | 36 / 320（11.3%） | 36 / 320 | 36 / 320 |
| 全部候选三元组相似度为 0 的查询 | 136 / 320（42.5%） | 132 / 320（41.3%） | 132 / 320（41.3%） |
| 查询延迟 p50 / p95 | 4.1 / 6.4 ms | 5.7 / 10.3 ms | 10.5 / 17.5 ms |

说明：

- “仅 FTS”只对少数能整词成句命中的风格偏好有效（原词片 0.36），对改写与时间
  指代完全为 0。
- 规定路径的改写/时间片命中里，有相当一部分并非相似度排序的结果，而是所有候选
  并列 0 分时按创建时间倒序产生的偶然命中；因此 0.61 / 0.45 不能当作“关键词能力”
  的上界，只能当作“原生 PG 中文关键词路径”的实际表现。
- 字符二元组对照命中 0.87 / 0.80，说明只要中文被切成可匹配的短单元，关键词路径
  在本题语料上是可用的；但它仍是评测代码，不是生产设计。

## 6. 中文分词限制与实际处理

- 本环境没有 zhparser / pg_jieba 等中文分词扩展，只有 `pg_trgm` 1.6。
- 实测处理顺序：`to_tsvector('simple', ...)` + `to_tsquery` OR + `ts_rank_cd`
  排序 → 结果不足 8 条时用 `word_similarity` 的三元组兜底补足。
- 实际影响（已量化）：
  - 原生 FTS 把整句中文当作一个词元，320 条查询里只有 36 条产生任何 FTS 命中
    （11.3%），整体 FTS-only recall 仅 0.1125。
  - `pg_trgm` 需要连续 3 个字符才有重叠；两字词嵌入在长句中时相似度为 0
    （例如“早市”对“去了早市买菜”）。42.5% 的查询对所有候选都是 0 分。
  - 因此中文关键词召回不能直接照搬英文 `tsvector + trigram` 方案；至少需要
    分词扩展或字符 n-gram（二元组）匹配。S4 实现必须显式选择其中之一，并在
    PR 中给出中文召回证据。
- 报告同时给出二元组对照，是为了让“向量必要性”的判断不被缺失的分词器误导；
  该对照不进入运行时，也不改变 ADR 的门槛定义。

## 7. 建议上限对照表（供产品定政策）

| 方案 | 12 个月留存 | 记忆视界（约） | 每用户文本 | 隐私/擦除面 | prune p95 | 适用判断 |
| --- | --- | --- | --- | --- | --- | --- |
| 48 / 16,000 | 40.7%（355/873） | ~5 个月 | ≤16 KB | 最小 | 9.8 ms | 仅适合短周期试用，不足以支撑长期记忆承诺 |
| **96 / 32,000（建议）** | **81.6%（712/873）** | **~10 个月** | **≤32 KB** | 中等 | **10.0 ms** | 覆盖大多数用户的一年内回溯，成本与保留面平衡 |
| 200 / 64,000 | 100%（873/873） | ≥12 个月 | ≤43.5 KB | 最大 | 11.3 ms | 产品明确承诺 >12 个月记忆时采用 |

补充建议：

1. 条数与字符必须成对设定：只提高条数而不提高字符，会让长笔记用户毫无收益。
2. 无论选哪档，都必须向用户说明记忆是**有界滚动**的，滚出不等于隐私擦除。
3. 上限是策略参数，写入 `retention_policy_version`；变更需重评估旧版本笔记，
   不允许混合版本直接服务。

## 8. 对向量五门的判断（当前语料）

| 门 | 阈值 | 本次结果 | 是否触发 |
| --- | --- | --- | --- |
| 1 召回缺口 | 优化后关键词 recall@8 < 0.85 或改写片 < 0.75 | 二元组对照 0.8688 / 0.8000 | **否** |
| 2 混合增益 | 整体 ≥10pp、改写 ≥15pp、无分片退化 >2pp | 未测（门 1 未触发，不进入） | 不适用 |
| 3 延迟 | 本地 embedding 召回 p95 ≤ 150 ms | 未测 | 不适用 |
| 4 删除可验证 | 删除演练通过 | 未做 | 不适用 |
| 5 真实规模/伤害压力 | 存在并复现 | 仅合成、词面可分语料 | 不满足 |

结论：**当前不启用向量。** 本语料的目标实体具有唯一锚点，词面可分性偏乐观；
在做出“关键词足够”的最终结论前，应补一轮更难但仍合成的语料（同义/多主题/
多笔记共享词），复核门 1–2。

## 9. 限制

- 单一 PG18 实例、单线程顺序执行；未模拟并发 prune、连接池竞争或真实磁盘抖动。
- 提炼桩不含模型生成时间；线上必须异步/尽力而为，且以清理边界保底（先落库或
  记录缺口，生成失败不阻塞 prune）。
- 按周切分窗口是建模选择；真实运行时按 token 预算推进 `C`，单次窗口可能更大。
- 语料不含 `statement_evidence`，因此 prune 未覆盖“被引用消息受保护”的分支；
  该分支已有独立 PG 集成测试，不在本基准范围。
- 召回只在评测代码中实现；没有验证 HTTP、feature flag、并发或缓存行为。
- 查询与标注由同一生成器派生，可能存在生成器偏置；fixture 已尽量提供可人工复核的
  锚点、日期与理由。

## 10. 复现

```bash
# 一次性 PG18（带 pgvector，基线迁移需要），独立端口/库
docker run -d --name bodysense-episodic-bench-pg \
  -e POSTGRES_PASSWORD=benchlocal -e POSTGRES_DB=bodysense_bench \
  -p 55432:5432 pgvector/pgvector:pg18
# 依次执行 apps/api/migrations/000001..000006 的 up 迁移，并 CREATE EXTENSION pg_trgm;

cd apps/api
go run ./benchmarks/episodic -write-fixtures
BODYSENSE_EPISODIC_BENCH_DSN='postgres://postgres:benchlocal@127.0.0.1:55432/bodysense_bench?sslmode=disable' \
  GIT_COMMIT=$(git rev-parse HEAD) \
  go run ./benchmarks/episodic
```

预期输出与 `results/benchmark.json` 一致（延迟除外）。harness 每次运行前会删除并
重建自己的合成用户，因此可重复执行。
