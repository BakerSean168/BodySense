# BodySense · 业务领域状态架构

正式领域规则见 [领域模型与数据契约](../product/domain/README.md)。本文说明领域状态的执行与持久化边界。

## 聚合与状态所有权

- **BodyState**：一个用户一份，保存当前的结构化身体状态、观察、推测、证据引用、安全状态与真实时间历史。
- **Diagnosis**：一个用户一份当前综合聚合，包含稳定身份的 ConditionEntry，任何有效的定向变更以整体原子事务提交。
- **TrainingPlan**：零到多份独立当前计划，各自具有执行记录、修改提案和授权的计划级修订。
- **Conversation**：交流与交互执行历史，不是上述领域事实的替代数据库。
- **Profile**：账号与稳定身份信息；健康测量、活动及身体变化有独立时间记录。

## 后端服务边界

~~~text
Web：提交用户意图、呈现当前状态、承载交互审批
   │ HTTP/SSE
   ▼
Go API：用户权限、业务事务、聚合修订、幂等与安全决策
   │ 结构化请求/响应
   ▼
Python Agent：模型推理、提取、自检、工具选择与交互续跑
   │
   └─ 知识检索、文件证据、自测与模型服务

PostgreSQL：业务对象、可追溯历史、审批与事件持久化
~~~

Agent 可以提交明确本人陈述形成候选命令，Go 验证后可直接记录为用户自述事实；这不是把 AI 医学推测提升为已确认病情。

## 原子写入语义

1. 用户归属、来源、时间有效区间、字段含义通过服务端校验。
2. 每次写入以幂等键防重；适用时校验基础修订，避免并发覆盖。
3. 修正错误记载与新增真实时间变化是两种不同操作。
4. 正式 Diagnosis 需要用户请求或授权、用户在 confirm_condition 中对每个病情提案的决定，以及证据/安全决策；同一次分析的生效决定一次原子提交，范围补丁保留未触及病情（确认规则见 [agent-workflows §3.2](../product/agent-workflows.md#32-diagnosis-正式分析与病情确认)）。
5. 训练计划内容只有明确用户请求或已接受的相关建议才可更新。
6. 安全执行限制可以独立发布，不等同于计划内容修订。

历史事实、诊断分析与训练修订均应能追溯其原始来源，但日常业务 UI 不展示技术修订管理。
